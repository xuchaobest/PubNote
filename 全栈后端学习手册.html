1.3 异步编程核心：Promise 与 async/await

后端几乎所有操作都是异步的（数据库、网络、文件），这是最核心的基础能力。

三种异步写法

// 1. 回调地狱（弃用）
db.query('SELECT * FROM users', (err, res) => {
  if (err) throw err;
  db.query('SELECT * FROM posts', (err2, res2) => {
    // 嵌套层级越多越难维护
  });
});

// 2. Promise 链式
db.query('SELECT * FROM users')
  .then(res => {
    return db.query('SELECT * FROM posts');
  })
  .then(res2 => { ... })
  .catch(err => { ... });

// 3. async/await（推荐，同步写法）
async function getData() {
  try {
    const users = await db.query('SELECT * FROM users');
    const posts = await db.query('SELECT * FROM posts');
    return { users, posts };
  } catch (err) {
    console.error('查询失败:', err);
    throw err;
  }
}

并发控制

// 串行：一个执行完再执行下一个（顺序依赖）
const a = await taskA();
const b = await taskB();

// 并行：同时执行，全部完成返回（无依赖，提升性能）
const [a, b] = await Promise.all([taskA(), taskB()]);

// 竞速：谁先完成返回谁
const result = await Promise.race([taskA(), taskB()]);

1.4 代码阅读方法论：五步读懂任意 Node.js 项目

  1. 看 package.json（项目说明书）
    • scripts：所有命令入口（启动、构建、部署、测试）
    • dependencies：生产依赖，判断项目用到了哪些技术
    • main：入口文件位置
  2. 找入口文件

    CloudBase 云函数入口一般是 index.js，先看导出的主函数 exports.main，理解入参（event, context）和出参格式。

  3. 顺调用链梳理分层

    标准链路：入口函数 → 业务逻辑层（service） → 数据访问层（repository） → 数据库

    不用逐行看懂细节，先理清「数据从哪来、经过什么处理、返回什么」。

  4. 看配置与常量

    环境变量、数据库配置、第三方密钥，一般在 .env、config/ 目录。

  5. 看目录结构

    通过目录判断项目分层：controllers/控制层、services/业务层、models/模型层、utils/工具类。

1.5 后端标准分层架构

好的后端项目一定是分层的，每层职责单一，和 iOS 的 MVC/MVVM 分层思想一致。

层级职责类比iOS
入口层（Handler/Controller）接收请求、参数校验、鉴权、统一返回格式ViewController
业务层（Service）核心业务逻辑、事务控制、业务校验ViewModel/业务逻辑层
数据访问层（Repository/DAO）数据库操作、SQL 封装，只做增删改查数据持久层
模型层（Model）数据实体定义、字段映射Model
工具层（Utils/Common）通用工具、加密、日期、响应封装通用工具类

云函数分层示例（项目可直接套用）

// index.js 入口层
const { auth } = require('./utils/auth');
const { createBubbleService } = require('./services/bubbleService');
const { success, fail } = require('./utils/response');

exports.main = async (event, context) => {
  try {
    // 1. 鉴权
    const userId = await auth(event);
    // 2. 参数校验
    if (!event.content) return fail(4000, '内容不能为空');
    // 3. 调用业务层
    const result = await createBubbleService(userId, event);
    // 4. 统一返回
    return success(result);
  } catch (err) {
    console.error('创建项目失败:', err);
    return fail(5000, '创建失败');
  }
};

1.6 企业级接口契约规范

接口不是能跑就行，统一的契约规范是团队协作、线上排错、多端适配的基础。

1. 统一返回格式

{
  code: 0,      // 业务状态码：0成功，非0失败
  message: '',  // 提示文案，失败时返回错误原因
  data: {}      // 业务数据
}

2. 错误码体系（分段定义，避免乱码）

码段含义示例
0成功操作成功
4000-4999客户端错误参数错误、格式非法、请求不存在
4010未授权token 失效、未登录
4030权限不足无操作权限
4290请求限流请求过于频繁
5000-5999服务端错误内部异常、数据库失败
5003第三方服务失败大模型、短信服务异常

3. 参数校验（入口第一道防线）

所有入参必须在入口处校验，不合法直接返回，不进入业务逻辑，保护后端服务。

const Joi = require('joi');

// 定义校验规则
const schema = Joi.object({
  content: Joi.string().required().max(500),
  isAnonymous: Joi.boolean().default(false),
  tags: Joi.array().items(Joi.string()).max(5)
});

// 入口校验
const { error, value } = schema.validate(event);
if (error) {
  return {
    code: 4000,
    message: '参数错误：' + error.details[0].message
  };
}

4. 幂等性设计

幂等 = 同一个请求调用 1 次和 N 次，结果完全一致。防止重复提交、网络重发导致数据异常。

常用实现方案：

  • 唯一幂等号：前端生成唯一 requestId，服务端记录已处理请求，重复请求直接返回成功
  • 数据库唯一索引：用户ID+业务类型建唯一索引，重复插入直接报错
  • 先查后插：写入前先判断是否已存在，不存在才执行

1.7 鉴权体系：JWT 实现与最佳实践

什么是 JWT

JSON Web Token，是目前最主流的无状态鉴权方案：用户登录后服务端签发 token，后续请求携带 token，服务端校验即可识别用户。

核心流程

  1. 用户登录成功 → 服务端用密钥签发 JWT（包含用户ID、过期时间）
  2. 前端保存 token，后续请求放在 header 里
  3. 接口入口处校验 token 合法性、有效期
  4. 解析出用户ID，注入业务逻辑

代码示例

const jwt = require('jsonwebtoken');
const SECRET_KEY = process.env.JWT_SECRET; // 密钥从环境变量读取

// 签发 token
function generateToken(userId) {
  return jwt.sign(
    { userId },
    SECRET_KEY,
    { expiresIn: '7d' } // 7天过期
  );
}

// 校验 token
function verifyToken(token) {
  try {
    const payload = jwt.verify(token, SECRET_KEY);
    return payload.userId;
  } catch (err) {
    return null; // 过期或非法
  }
}
⚠️ 安全红线：密钥绝对不能硬编码在代码里，必须从环境变量配置；使用 HS256 算法，密钥长度足够；遵循 fail-closed 原则：校验失败直接拒绝，不放通。

1.8 限流与熔断基础

为什么要限流

防止恶意请求、突发流量打垮服务，保护系统可用性。

常用限流算法

算法原理优缺点
固定窗口计数每分钟最多 N 次，到点清零实现简单，边界有突刺问题
滑动窗口记录最近一分钟的请求数，平滑滑动更平滑，实现稍复杂
令牌桶匀速生成令牌，请求消耗令牌允许突发流量，最常用

熔断降级

第三方服务（如大模型、短信）不可用时，快速失败，不要拖垮主服务。

  • 失败累计到阈值，触发熔断，一段时间内直接返回失败
  • 熔断后定期探测，服务恢复后自动关闭熔断
  • Fail-Closed 原则：依赖的服务/密钥缺失时，默认拒绝服务，而不是放通，避免安全风险

2.2 表设计规范与最佳实践

命名规范（企业级标准）

  • 表名、字段名全部 snake_case（下划线小写），如 user_profile、created_at
  • 表名用复数，如 users、bubbles、comments
  • 主键统一叫 id，类型用 BIGSERIAL 自增或 UUID
  • 必须包含三公共字段：created_at（创建时间）、updated_at（更新时间）、deleted_at（软删除）
  • 索引统一前缀 idx_表名_字段名，唯一索引前缀 uk_表名_字段名

常用字段类型

类型说明示例
BIGSERIAL自增 64 位整数，主键专用id BIGSERIAL PRIMARY KEY
VARCHAR(n)变长字符串，n 为最大长度username VARCHAR(50) NOT NULL
TEXT长文本，无长度限制content TEXT
INTEGER / BIGINT整数view_count INTEGER DEFAULT 0
NUMERIC(10,2)精确小数，用于金额price NUMERIC(10,2)
BOOLEAN布尔值is_active BOOLEAN DEFAULT true
TIMESTAMPTZ带时区时间created_at TIMESTAMPTZ DEFAULT NOW()
JSONB二进制 JSON，可索引extra JSONB DEFAULT '{}'::jsonb

表设计六大原则

  1. 单一职责：一张表只描述一个实体，避免大而全的表
  2. 适度冗余：为查询性能，可适当冗余字段，避免频繁联表
  3. 软删除优先：用 deleted_at 软删除，保留数据痕迹
  4. 非空约束：必填字段加 NOT NULL，从数据库层保证数据完整性
  5. 合理默认值：状态、时间、数字尽量设置默认值
  6. 禁止物理删除：重要业务数据不做 DELETE 操作

1. 建表（CREATE TABLE）

-- 基础条件查询
SELECT id, username, nickname FROM users 
WHERE is_active = true AND deleted_at IS NULL;

-- 分页查询
SELECT * FROM bubbles 
ORDER BY created_at DESC 
LIMIT 10 OFFSET 20;

-- 模糊搜索
SELECT * FROM bubbles 
WHERE content LIKE '%关键词%' 
  AND status = 'published';

-- 联表查询
SELECT b.id, b.content, u.nickname AS author
FROM bubbles b
JOIN users u ON b.user_id = u.id
WHERE b.deleted_at IS NULL;

-- 聚合统计
SELECT user_id, COUNT(*) as bubble_count 
FROM bubbles 
GROUP BY user_id
HAVING COUNT(*) > 5;

2.4 索引设计与性能优化

索引的本质

索引就像书的目录，通过额外的存储空间，大幅提升查询速度，但会降低写入速度。不是越多越好，只给高频查询字段加。

索引使用场景

  • ✅ WHERE 条件中频繁出现的字段
  • ✅ JOIN 关联的字段
  • ✅ ORDER BY 排序的字段
  • ✅ GROUP BY 分组的字段
  • ❌ 数据量很小的表（几百条以内）
  • ❌ 频繁更新的字段（索引维护成本高）
  • ❌ 区分度很低的字段（如性别、状态只有2-3个值）

查看执行计划（排查慢查询）

EXPLAIN ANALYZE
SELECT * FROM bubbles WHERE user_id = 123 ORDER BY created_at DESC;

结果中出现 Seq Scan = 全表扫描（慢），出现 Index Scan = 索引扫描（快）。全表扫描就要考虑加索引。

2.5 触发器与自动更新

触发器是数据库内置功能，数据变更时自动执行逻辑，比代码层更可靠。

经典场景：自动更新 updated_at

-- 创建触发器函数
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 给表绑定触发器
CREATE TRIGGER update_bubbles_updated_at
BEFORE UPDATE ON bubbles
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();

其他适用场景

  • 数据变更时自动记录操作日志
  • 数据变更触发关联数据更新
  • 写入前数据校验、格式化

2.6 RLS 行级权限策略

RLS（Row Level Security）是 PostgreSQL 高级特性，CloudBase 深度集成，在数据库层面实现「用户只能看到自己的数据」，比代码层判断更安全。

-- 开启表的 RLS
ALTER TABLE bubbles ENABLE ROW LEVEL SECURITY;

-- 查询策略：只能看自己的泡泡
CREATE POLICY bubble_select ON bubbles
  FOR SELECT USING (user_id = current_setting('app.current_user_id')::bigint);

-- 插入策略：只能插入自己的泡泡
CREATE POLICY bubble_insert ON bubbles
  FOR INSERT WITH CHECK (user_id = current_setting('app.current_user_id')::bigint);

-- 更新策略：只能更新自己的泡泡
CREATE POLICY bubble_update ON bubbles
  FOR UPDATE USING (user_id = current_setting('app.current_user_id')::bigint);
💡 核心价值：RLS 遵循 fail-closed 原则，没有匹配策略的操作默认被拒绝，绕开代码层也无法越权访问，是 CloudBase 项目的核心安全机制。

2.7 事务与并发控制

什么是事务

事务是一组 SQL 操作，要么全部成功，要么全部失败，保证数据一致性。

ACID 四大特性

  • 原子性（Atomicity）：事务内操作不可分割
  • 一致性（Consistency）：事务前后数据保持一致
  • 隔离性（Isolation）：多个事务互不干扰
  • 持久性（Durability）：事务提交后永久生效

代码示例

BEGIN; -- 开启事务

2.8 企业级数据库迁移治理体系

迁移就是把表结构变更代码化、版本化，保证开发、测试、生产环境表结构完全一致，是企业级项目的标配。

核心原则：基线冻结 + 严格增量 + 迁移台账

  1. 基线冻结：初始表结构作为基线版本，一旦发布不再修改
  2. 严格增量：所有表结构变更都通过新增迁移文件实现，不修改已有迁移文件
  3. 迁移台账：数据库中记录表，记录已执行的迁移版本，避免重复执行
  4. 可回滚：每个迁移都对应回滚方案，出错能快速恢复
  5. 幂等执行：迁移脚本重复执行不会出错

迁移文件命名规范

序号_描述.sql，序号按时间递增，如：

  • 001_init_users.sql
  • 002_create_bubbles.sql
  • 003_add_bubbles_view_count.sql

迁移脚本结构

-- 升级
CREATE TABLE comments (
  id BIGSERIAL PRIMARY KEY,
  bubble_id BIGINT NOT NULL REFERENCES bubbles(id),
  user_id BIGINT NOT NULL REFERENCES users(id),
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
);

CREATE INDEX idx_comments_bubble_id ON comments(bubble_id);
CREATE INDEX idx_comments_user_id ON comments(user_id);

-- 回滚
-- DROP TABLE comments;

迁移执行流程

  1. 本地编写迁移脚本
  2. 本地执行迁移，验证功能
  3. 提交代码，测试环境执行
  4. 上线前预发布环境执行
  5. 生产环境低峰期执行
⚠️ 线上红线：大表 ALTER TABLE 可能锁表，导致业务暂停。数据量大的表必须选低峰期操作，或使用平滑迁移方案。

2.9 数据库安全最佳实践

  • 最小权限原则：数据库账号只给必要权限，不给超级权限
  • 密码强复杂度，定期轮换
  • 敏感数据加密存储：密码用 bcrypt 哈希，不存明文
  • 开启 RLS 行级权限，数据按用户隔离
  • SQL 注入防护：使用参数化查询，不拼接 SQL 字符串
  • 定期备份，验证备份可恢复

3.1 云函数核心概念进阶

什么是 Serverless 云函数

运行在云端的事件驱动代码，无需管理服务器，按需运行，按量计费。平台自动处理扩容、容灾、运维。

核心特性

  • 无服务器：不用管机器、操作系统、进程
  • 按需计费：调用才收费，空闲不花钱
  • 自动扩容：高并发时平台自动增加实例
  • 冷启动：长时间不调用，实例销毁，下次调用需重新初始化，有几百毫秒延迟
  • 无状态：函数实例可能随时销毁，全局变量不保证持久化

触发方式

触发方式说明适用场景
SDK 调用Flutter 端通过 SDK 直接调用App 内业务接口，最常用
HTTP 触发生成 URL，HTTP 请求调用第三方回调、外部系统对接
定时触发按 Cron 表达式定时执行每日统计、数据清理、定时推送
数据库触发表数据增删改时触发数据变更同步、消息通知
存储触发文件上传/删除时触发图片处理、文件转码

3.2 云函数分层架构与模块化

标准分层结构

  • 入口层：只做请求接入，不写业务逻辑

  • 数据层：只做数据库操作，不包含业务判断
  • 工具层：通用能力，可被所有函数复用

3.4 配置管理与配置漂移治理

配置漂移是什么

不同环境、不同函数的配置不一致，导致测试正常、线上出问题，是 Serverless 项目的常见坑。

配置管理三大原则

  1. 代码配置分离：密钥、环境 ID、地址绝对不硬编码，全部走环境变量
  2. 环境隔离：开发、测试、生产配置独立，互不干扰
  3. 集中管理：公共配置统一维护，避免每个函数各自配置

配置分层

  • 全局配置：数据库地址、密钥等，所有函数共享
  • 函数配置：单个函数的超时、内存、特有参数
  • 环境配置：不同环境的差异配置

配置漂移治理方案

  1. 配置文件代码化，提交到 Git 仓库，变更有记录
  2. 使用配置文件统一管理所有函数配置，部署时自动注入
  3. 定期巡检线上配置与代码中配置是否一致
  4. 新增配置必须同步更新所有环境，不能只改生产

3.5 函数注册与自检机制

为什么需要自检

云函数数量多了之后，容易出现部署失败、配置缺失、依赖报错等问题，上线后才发现。自检机制可以在部署后自动验证函数可用性。

自检实现方案

  1. 每个函数提供一个 health 检查入口
  2. 部署完成后，自动调用所有函数的健康检查接口
  3. 验证：数据库连接正常、配置加载正常、依赖可用
  4. 自检失败，部署流程中断，告警通知

健康检查示例

exports.health = async () => {
  try {
    // 验证数据库连接
    await db.query('SELECT 1');
    // 验证关键配置
    if (!process.env.JWT_SECRET) throw new Error('JWT_SECRET 缺失');
    
    return { status: 'ok', code: 0 };
  } catch (err) {
    return { status: 'error', message: err.message, code: 500 };
  }
};

3.7 冷启动优化与性能调优

冷启动产生的原因

函数长时间没有调用，平台会销毁实例；下次调用需要重新初始化环境、加载代码、建立连接，产生几百毫秒到几秒的延迟。

优化手段

  1. 减小部署包体积
    • 只安装生产依赖，移除 devDependencies
    • 删除不必要的文件、文档、测试代码
    • 大的依赖包按需加载，不要在顶部 require
  2. 初始化外置

    数据库连接、SDK 初始化放在函数外面，全局只初始化一次，实例复用时不用重复初始化。

    // ✅ 好：全局初始化，冷启动只执行一次
const db = require('./db').init();

exports.main = async (event) => {
  // 直接使用 db
};

// ❌ 坏：每次调用都初始化
exports.main = async (event) => {
  const db = require('./db').init(); // 每次都重新连接
};
  3. 合理配置资源
    • 普通接口：256MB 内存，3-5 秒超时
    • 计算密集型：512MB 或 1GB 内存
    • AI 任务：2GB 内存，30-60 秒超时
  4. 预置并发

    核心接口配置常驻实例，消除冷启动延迟；会增加成本，只给核心接口用。

  5. 定时预热

    用定时函数每隔几分钟调用一次核心接口，保持实例存活。

3.8 云函数测试策略

1. 单元测试

针对单个函数、单个模块，模拟依赖，验证逻辑正确性。

  • 业务逻辑、工具函数必须写单测
  • 数据库、第三方接口用 mock 模拟
  • 覆盖正常、异常、边界场景

2. 集成测试

部署到测试环境，真实调用，验证全链路是否正常。

  • 测试真实数据库、真实依赖
  • 验证接口入参出参、业务流程
  • 核心路径必须覆盖

3. 冒烟测试

上线前快速验证核心功能是否可用，不用测全量。

  • 部署后立即调用核心接口
  • 验证主流程能跑通
  • 冒烟不通过，直接回滚

4.1 多环境体系设计

为什么需要多环境

开发、测试、生产严格隔离，避免开发操作影响线上数据，保证发布质量。

标准四环境体系

环境用途数据稳定性部署频率
开发环境（dev）开发者日常开发调试测试数据，可随便改低随时
测试环境（test）测试人员功能测试模拟真实数据中每日/按提测
预发布环境（pre）上线前最后验证生产数据快照高版本发布前
生产环境（prod）正式用户使用真实用户数据极高按版本计划
⚠️ 红线：绝对不能在生产环境直接改代码、测功能！所有变更必须经过开发→测试→预发→生产的流程。

CloudBase 多环境实现

  1. 在 CloudBase 控制台创建多个独立环境，分别命名 dev、test、prod
  2. 每个环境有独立的环境 ID、独立数据库、独立云函数、独立存储
  3. 数据库表结构通过迁移文件保证一致
  4. 代码同一套，通过环境变量区分配置

4.2 环境配置隔离与密钥管理

配置分类

类型举例存放位置
非敏感配置超时时间、分页大小、功能开关代码配置文件、环境变量
敏感配置数据库密码、密钥、Token环境变量、密钥管理服务

配置管理最佳实践

  1. 配置与代码分离：所有环境相关配置都不写死在代码里
  2. 环境变量优先：通过系统环境变量注入，不同环境自动加载对应配置
  3. 密钥不上代码库：.env 文件加入 .gitignore，只提交 .env.example 模板
  4. 配置集中管理：公共配置统一维护，避免分散在各个函数里
  5. 变更可追溯：配置变更有记录，能回滚

前端多环境配置（Flutter）

  • 创建不同入口文件：main_dev.dart、main_test.dart、main_prod.dart
  • 每个入口配置不同的 CloudBase 环境 ID、接口地址
  • 打包时指定入口：flutter build ios -t lib/main_prod.dart

5.3 日志规范与问题排查方法论

日志要记录什么

  • 关键业务节点：创建、更新、删除等操作
  • 所有错误异常：必须带错误栈、上下文信息
  • 第三方调用：入参出参、耗时、结果
  • 关键数据变更：变更前后对比、操作人

排查问题五步法

  1. 收集信息：什么问题？什么时候出现？影响范围？有没有复现路径？
  2. 复现问题：尽量在测试环境复现，确定稳定复现步骤
  3. 缩小范围
    • 是前端问题还是后端问题？
    • 是哪个接口、哪个模块出的错？
    • 是数据库、业务逻辑还是第三方服务？
  4. 定位根因：查日志、看错误栈、定位到具体代码行
  5. 验证修复：修复后验证，确认问题解决，回归测试
💡 排查技巧：先看错误信息，再看日志上下文，不要上来就猜。90% 的问题日志里都有答案。

5.4 线上故障分级与应急响应

故障分级

级别定义响应时间处理优先级
P0 致命核心功能不可用，大量用户受影响立即响应最高，停止一切其他工作
P1 严重重要功能异常，部分用户受影响30分钟内响应高，优先处理
P2 一般普通功能bug，少量用户工作日内正常迭代修复
P3 轻微体验问题、文案错误排期修复低

P0 故障处理流程

  1. 止损优先：先恢复服务，再排查原因。能回滚先回滚，能降级先降级
  2. 同步信息：及时同步给相关人，说明影响范围、处理进度
  3. 定位修复：快速定位问题，临时修复方案
  4. 验证恢复：确认服务恢复正常
  5. 事后复盘：根因分析、改进措施、避免再发生
⚠️ 重要原则：线上故障先止损，不要死磕根因耽误时间。用户体验和服务可用性是第一位的。

5.5 性能优化实战方法论

性能优化通用步骤

  3. 做优化：针对瓶颈点优化
  4. 再验证：优化后效果怎么样？有没有达到目标？有没有副作用？

瓶颈优化手段

5.6 稳定性兜底七板斧

高可用系统的标配手段，保障系统在各种异常情况下依然可用。

1. 幂等

同一个请求调用多次结果一致，防止重复提交、网络重发导致数据错误。

2. 重试

网络抖动、临时失败时，自动重试，提升成功率。

  • 只读接口可以重试，写入接口要配合幂等
  • 指数退避：重试间隔逐渐变长
  • 设置最大重试次数，避免无限重试

3. 熔断

依赖的第三方服务挂了，快速失败，不要拖垮自己。

  • 失败率达到阈值，触发熔断
  • 熔断期间直接返回错误，不调用下游
  • 定期探测，恢复后自动关闭熔断

4. 降级

系统压力大时，暂时关闭非核心功能，保证核心功能可用。

  • 比如推荐功能挂了，保证列表浏览正常
  • 通过功能开关控制，一键降级

5. 限流

限制请求频率，防止恶意刷接口、突发流量打垮系统。

6. 缓存

热点数据放缓存，减少数据库压力，提升响应速度。

  • 适合读多写少的数据
  • 注意缓存一致性、缓存过期策略

7. 隔离

不同业务、不同模块隔离，一个出问题不影响其他。

  • 核心功能和非核心功能隔离
  • 第三方调用单独线程池/实例

5.8 版本发布与灰度回滚

标准发布流程

  1. 需求评审 → 技术方案 → 开发 → 测试
  2. 预发布环境验证，用真实数据场景测试
  3. 选择低峰期发布（如凌晨、非工作日）
  4. 先执行数据库迁移
  5. 再部署云函数/前端
  6. 发布后立即冒烟测试，验证核心功能
  7. 发布后观察 1-2 小时，监控指标是否正常

灰度发布

新版本不一下子全量上线，先给一小部分用户用，验证没问题再逐步放开，降低风险。

  • 按用户 ID 灰度：先给 1% 用户开放
  • 按设备灰度：内测用户先体验
  • CloudBase 云函数支持版本管理，实现流量灰度

回滚机制

上线后发现严重问题，快速回退到上一个稳定版本。

  • 云函数：控制台切换回上一个版本，1分钟内完成
  • 数据库：回滚迁移脚本，或从备份恢复
  • 前端：App 发布无法快速回滚，所以必须更谨慎，先灰度再全量

6.1 AI 工程化核心认知

什么是 AI 工程化

把 AI 能力稳定、可靠、低成本地集成到产品中，而不是简单的 API 调用。要考虑容错、成本、性能、安全、可运维。

AI 集成常见坑

  • 单一大模型服务商，挂了就全挂
  • 不做成本控制，月底账单爆炸
  • 同步调用大模型，接口超时
  • 输入不做校验，被注入攻击
  • 没有用量监控，超了都不知道

6.2 统一 LLM 接入层架构设计

为什么需要统一接入层

  • 屏蔽不同厂商的 API 差异，业务层不用关心具体服务商
  • 方便切换、新增服务商，不用改业务代码
  • 统一做限流、熔断、计费、日志

分层架构

业务层 → 统一AI网关 → 服务商适配层 → 各大模型服务商

核心能力

  • 统一的调用接口
  • 多服务商自动切换
  • 失败重试与降级
  • Token 用量统计
  • 输入输出安全校验
  • 成本控制与告警

6.3 多提供商容错与降级策略

核心思路

不要把鸡蛋放一个篮子里。配置多个模型服务商，一个挂了自动切另一个，保障可用性。

策略实现

  1. 主备模式：默认用主服务商，失败自动切备用服务商
  2. 均分流量：请求按比例分给多个服务商，避免单家超限
  3. 按场景选型：简单任务用便宜模型，复杂任务用好模型

失败降级链路

调用主模型 → 失败 → 重试1次 → 再失败 → 切换备用模型 → 再失败 → 返回降级结果
💡 设计原则：fail-soft 优先。AI 能力属于增强功能，不能因为 AI 挂了导致主业务不可用。极端情况返回兜底结果，保证主流程通畅。

6.4 输入裁剪与 Token 成本控制

Token 是什么

大模型按 Token 计费，Token 是模型处理文本的单位，大概 1000 Token ≈ 700 汉字。输入输出都计费，控制输入长度就是省钱。

成本优化手段

  1. 输入裁剪
    • 移除不必要的上下文、冗余信息
    • 长文本先摘要，再送入模型
    • 设置最大输入长度限制，超长截断
  2. 输出限制
    • 设置 max_tokens，限制输出长度
    • 明确指令，让模型简洁回答
  3. 选型优化
    • 简单任务用轻量模型，便宜又快
    • 复杂任务才用高级模型
  4. 缓存复用
    • 相同的问题缓存答案，不用重复调用
    • 高频请求命中率很高，大幅省钱

6.5 异步任务队列架构（AI 生图典型场景）

为什么用异步

AI 生图、长文本生成耗时久（几秒到几十秒），同步调用会导致接口超时、用户等待。异步架构：提交任务 → 后台处理 → 完成通知。

架构组成

组件作用
任务提交接口接收请求，入队，返回任务ID
任务队列待处理任务排队，削峰填谷
Worker 进程定时拉取任务，执行 AI 调用
任务状态表记录任务状态、进度、结果
结果查询/通知用户查询进度，完成后推送通知

任务状态机

  • pending：等待处理
  • processing：处理中
  • success：成功
  • failed：失败

租约式任务领取

避免多个 Worker 重复处理同一个任务：

  1. Worker 领取任务时，加锁并设置租约过期时间
  2. 规定时间内没处理完，租约过期，其他 Worker 可以重新领取
  3. 处理完成，标记成功
  4. 失败回退到 pending，可重试

CloudBase 实现方案

  • 数据库表存任务，状态字段标记进度
  • 定时云函数作为 Worker，每分钟拉取待处理任务
  • 处理完成更新任务状态，存结果
  • 前端轮询查询任务状态，或用订阅消息通知

6.6 用量监控与成本护栏

用量统计

  • 每次调用记录 Token 用量、费用
  • 按用户、按天、按模型维度统计
  • 存入数据库，方便查询对账

成本护栏机制

  1. 单用户限额：每个用户每天/每月免费次数上限，超了收费或限制
  2. 全局日限额：整个项目每日预算上限，超了自动降级或暂停服务
  3. 超额告警：用到 80% 发告警通知，提前感知
  4. 异常熔断：短时间用量暴增，自动熔断，防止刷接口

6.7 Prompt 工程规范与安全

Prompt 编写原则

  • 角色明确：告诉模型扮演什么角色
  • 任务清晰：明确要做什么，输出格式是什么
  • 约束具体：限制范围、长度、风格
  • 示例引导：给例子，模型更容易符合预期

安全规范

  • 用户输入做过滤，防止提示词注入攻击
  • 敏感内容校验，输出违规内容拦截
  • 不把系统提示词暴露给前端
  • 用户输入和系统提示词分开，不直接拼接

7.5 架构设计基础思维

  3. 规模化：微服务、分库分表、多机房

八、项目实战落地清单
可直接执行的行动清单，按阶段推进，边学边练，把知识真正变成自己的能力。

8.1 第一阶段：现有项目梳理与规范化（1-2周）

  • ☐ 梳理所有云函数，按「入口→业务→数据」三层重构，分层清晰
  • ☐ 整理数据库所有表，输出表结构文档，标注字段含义、类型、索引
  • ☐ 梳理所有云函数的入参、出参、功能，输出接口文档
  • ☐ 统一所有接口返回格式，封装 success/fail 公共方法
  • ☐ 统一错误码定义，全项目对齐
  • ☐ 所有接口加入参数校验
  • ☐ 检查所有 SQL 语句，给常用查询字段补上索引
  • ☐ 代码里硬编码的配置全部改成环境变量
  • ☐ 给所有表加上 updated_at 自动更新触发器

8.2 第二阶段：工程化体系补全（2-3周）

  • ☐ 搭建开发、测试两套 CloudBase 环境，实现配置隔离
  • ☐ 完善数据库迁移机制，所有表结构变更都走迁移文件
  • ☐ 沉淀公共共享模块：鉴权、响应、数据库访问、限流
  • ☐ 配置 CloudBase CLI，实现命令行一键部署云函数
  • ☐ 统一 Git 提交规范，建立 main/develop/feature 分支策略
  • ☐ 编写部署脚本、迁移执行脚本，自动化重复操作
  • ☐ 给核心业务逻辑加上单元测试
  • ☐ 建立函数自检机制，部署后自动验证健康状态

8.3 第三阶段：运维与稳定性能力落地（1-2周）

  • ☐ 配置数据库自动备份策略，手动做一次恢复演练
  • ☐ 给所有云函数加上规范的错误日志，包含上下文信息
  • ☐ 整理线上问题排查手册，包含常见问题、排查步骤
  • ☐ 做一次完整的版本发布演练，走开发→测试→上线完整流程
  • ☐ 优化核心云函数冷启动性能，减小部署包体积
  • ☐ 核心接口实现幂等性，防止重复提交
  • ☐ 给重要接口加上限流保护
  • ☐ 设计版本回滚方案，验证可快速回退

8.4 第四阶段：AI 工程化深化（1-2周）

  • ☐ 重构 AI 调用为统一接入层，屏蔽服务商差异
  • ☐ 接入第二个大模型服务商，实现主备自动切换
  • ☐ 实现 Token 用量统计，按用户、按天维度记录
  • ☐ 加上成本护栏：单用户限额、全局日限额、超额告警
  • ☐ AI 生图改为异步任务队列架构，用定时 Worker 处理
  • ☐ 实现任务状态机、租约式领取、失败重试
  • ☐ 做输入裁剪优化，控制 Token 成本

8.5 第五阶段：企业级能力进阶（持续）

  • ☐ 学习事务、锁、并发控制等数据库高级知识
  • ☐ 做一次全量安全审计，检查权限、注入风险
  • ☐ 学习 CI/CD 流水线配置，实现提交自动部署测试环境
  • ☐ 研究灰度发布、限流降级等高可用方案
  • ☐ 持续优化成本，合理配置云函数资源，避免浪费
  • ☐ 定期复盘线上问题，沉淀方法论
