1.1基础筑基（第 1–2 月） 语言 + 数据库操作 ▶

PHP 语法与数据类型 核心

是什么：PHP 是弱类型服务端语言，变量以 $ 开头，无需声明类型。核心数据类型：标量（int/float/string/bool）、复合（array/object）、特殊（null/resource）。

  • 变量与超全局：$_GET/$_POST/$_REQUEST/$_SESSION/$_COOKIE/$_SERVER/$_FILES 是框架底层常用的输入来源，务必先了解。
  • 字符串处理：单引号不解析变量、双引号解析；常用函数 strlen/substr/str_replace/explode/implode/trim；中文处理用 mb_strlen/mb_substr。
  • 数组：PHP 数组同时支持索引与关联键，常用 array_map/array_filter/array_reduce/array_merge/usort 等高阶函数。
  • 严格模式：文件开头 declare(strict_types=1) 可开启严格类型约束，减少隐式转换 Bug。
为什么重要：所有框架（ThinkPHP/Laravel）都是基于这些语法特性封装，底层扎实才能读懂框架源码、排查线上问题。
注意：PHP 8+ 起强类型能力增强（联合类型、构造器属性提升、match 表达式），学习时以 PHP 8.x 为准。

面向对象（OOP）核心

是什么：以对象为核心组织代码。三大特性：封装（可见性 public/protected/private）、继承（extends）、多态（接口/抽象类实现同一行为）。

  • 接口与抽象类：接口约行为（implements），抽象类供复用（extends）；一个类可实现多接口、只可继承一个类。
  • Trait：代码复用片段，解决 PHP 单继承限制，用 use TraitName 引入。
  • 命名空间：namespace App\Service 组织代码，配合 use 引入，与目录结构一一对应。
  • 自动加载：Composer 的 PSR-4 自动加载把「命名空间 → 文件路径」映射，无需手动 require。
为什么重要：框架的 IoC 容器、依赖注入、门面（Facade）全部建立在 OOP 之上；面试必问「三大特性 + 设计原则」。

Composer 依赖管理 工程

是什么：PHP 的依赖管理工具（类似 npm/pip），通过 composer.json 声明依赖，composer install 安装到 vendor/。

  • 常用命令：composer require 包名、composer install（按锁文件）、composer update、composer dump-autoload。
  • 锁文件：composer.lock 固定精确版本，保证团队/生产环境一致，必须提交到版本库。
  • 语义化版本：^2.0 表示 >=2.0.0 <3.0.0；~2.1 表示 >=2.1.0 <2.2.0。

PDO 与 MySQL 基础操作 核心

是什么：PDO（PHP Data Objects）是统一数据库抽象层，支持预处理语句，是防 SQL 注入的标准方案。

// 连接 + 预处理 + 绑定参数（推荐写法）
$pdo = new PDO('mysql:host=127.0.0.1;dbname=test;charset=utf8mb4', 'root', 'pass');
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
$stmt = $pdo->prepare('SELECT * FROM users WHERE email = ?');
$stmt->execute([$email]);
$user = $stmt->fetch(PDO::FETCH_ASSOC);
  • 为什么用预处理：SQL 模板先编译、参数后绑定，用户输入永远不可能成为 SQL 代码 → 从机制上杜绝注入。
  • 事务：beginTransaction() → 操作 → commit()/rollBack()，保证多条写操作原子性。
  • 字符集：统一 utf8mb4（支持 emoji 与生僻字），连接与表、字段三处一致。
常见坑：不要用 mysql_query（已移除）；不要把用户输入直接拼进 SQL；字段值一律参数化。

1.2技术进阶（第 3–4 月） 框架 + API + 鉴权 ▶

HTTP 协议与请求响应模型 核心

是什么：HTTP 是无状态请求-响应协议。一次请求 = 请求行（方法+路径+版本）+ 请求头 + 请求体；响应 = 状态行 + 响应头 + 响应体。

  • 常见方法：GET（读，无副作用）、POST（新建）、PUT（整体更新）、PATCH（部分更新）、DELETE（删除）。
  • 状态码：2xx 成功 / 3xx 重定向 / 4xx 客户端错误（400 参数错、401 未认证、403 无权限、404 不存在、429 限流）/ 5xx 服务端错误（500、502 网关错、503 不可用、504 超时）。
  • 无状态：服务器不记会话 → 需 Cookie/Session 或 Token 方案维持登录态。
  • 常见请求头：Content-Type（application/json 等）、Authorization（Bearer Token）、Accept、User-Agent。

MVC 与主流框架（ThinkPHP / Laravel）核心

是什么：MVC 将代码分为 Model（数据）、View（展示）、Controller（业务编排）。框架在 MVC 之上提供路由、容器、ORM、中间件等能力。

  • ThinkPHP 8：国内常用，中文文档友好，适合快速开发与中小项目。
  • Laravel 11：生态最全（Eloquent ORM、Blade 模板、Artisan CLI、队列、事件），适合中大型与长期维护项目。
  • 生命周期：请求 → 入口 index.php → 框架引导（加载配置、注册服务）→ 路由匹配 → 中间件 → 控制器 → 模型/ORM 读写 → 响应返回。
  • 核心概念：路由定义、控制器方法、服务容器（IoC）、依赖注入、门面（Facade）、ORM（对象关系映射）。
为什么重要：「框架是工具，原理是内功」。面试官更看重你是否理解框架做了什么，而不只是会用。

路由与中间件 核心

是什么：路由把 URL 映射到控制器方法；中间件在请求进入控制器前后做统一处理（鉴权、日志、CORS、限流）。

// Laravel 路由 + 中间件示例
Route::middleware('auth:api')->group(function () {
    Route::get('/user/profile', [UserController::class, 'profile']);
    Route::post('/order', [OrderController::class, 'create']);
});
  • 中间件执行顺序：按注册顺序「洋葱模型」进入，响应再逆序返回。
  • 典型中间件：认证、CORS、请求日志、限流、参数校验、敏感操作审计。

RESTful API 设计规范 核心

是什么：以资源为中心设计接口：URL 表示资源，HTTP 方法表示动作，返回 JSON，无状态。

  • URL 设计：名词复数 + 层级：GET /api/users（列表）、POST /api/users（新建）、GET /api/users/1（详情）、PUT /api/users/1（更新）、DELETE /api/users/1（删除）。
  • 统一响应：{code:0, message:"ok", data:{...}}，前端按 code 判断业务成败。
  • 分页规范：?page=1&page_size=20，返回 total/items。
  • 错误语义：参数错误 400、未认证 401、无权限 403、不存在 404、限流 429。
  • 版本控制：/api/v1/... 便于演进。
提示：幂等性：GET/DELETE/PUT 应幂等（重复执行结果一致）；POST 不保证。

用户认证与 JWT 核心

是什么：JWT（JSON Web Token）无状态鉴权：登录成功后服务端签发令牌，客户端请求携带，服务端验签即信任。

  • 结构：Header.Payload.Signature，三段 Base64Url；Signature 用服务端密钥 HMAC-SHA256 计算。
  • 流程：登录 → 校验账号密码 → 签发 token（含 uid、过期时间 exp）→ 客户端存 token → 每次请求带 Authorization: Bearer <token> → 服务端验签解析。
  • 与 Session 对比：Session 存服务端（可主动失效、占用内存），JWT 存客户端（无状态、跨域友好、不可主动失效）。
  • 注意：token 放 localStorage 有 XSS 风险；敏感信息不要放 payload；过期时间不宜过长，配合刷新令牌。

参数校验与统一异常处理 规范

  • 入参校验：必填、类型、长度、枚举范围、邮箱/手机号格式；框架的 FormRequest / Validate 类集中管理。
  • 统一异常：全局捕获业务异常 → 返回统一 JSON；未捕获异常 → 记录日志 + 返回 500。
  • 日志分级：debug/info/warning/error，关键操作与异常必须留痕。

1.3中级实战（第 5–6 月） 缓存 + 队列 + 性能 + 安全 ▶

Redis 缓存实战 核心

是什么：Redis 是内存键值数据库，5 大数据类型：String、Hash、List、Set、ZSet（有序集合）。

  • 常用场景：热点数据缓存、Session 共享、分布式锁（SETNX + 过期）、计数器、排行榜（ZSet）、限流、消息队列（List/Stream）。
  • 缓存策略：读多写少 + 数据可容忍短暂不一致才缓存；key 命名规范 业务:模块:id。
  • 缓存穿透：查询不存在的数据 → 缓存与 DB 都无 → 恶意流量打穿。解决：缓存空值 + 布隆过滤器。
  • 缓存击穿：热点 key 过期瞬间大量请求打到 DB。解决：互斥锁重建缓存 + 逻辑过期。
  • 缓存雪崩：大量 key 同时过期 → 流量打垮 DB。解决：过期时间加随机值 + 多级缓存 + 限流降级。
  • 缓存与 DB 一致性：常用「先更新 DB 再删缓存」（Cache Aside）；极端一致性用延迟双删或 binlog 订阅。
为什么重要：「缓存三兄弟」（穿透/击穿/雪崩）是面试高频题，也是线上性能问题的三大根源。

数据库设计、索引与 SQL 优化 核心

是什么：表结构设计决定系统天花板；索引加速查询；SQL 优化是后端基本功。

  • 设计原则：三范式（避免冗余）与反范式（读多冗余列）平衡；字段类型选小不选大（int 优于 varchar）；主键用自增或雪花 ID。
  • 索引原理：InnoDB 用 B+ 树；聚簇索引（主键）叶子存整行，二级索引叶子存主键 → 回表概念由此而来。
  • 索引设计：where 条件列 + 排序列建索引；联合索引遵循最左前缀；区分度低的列（性别）不建单列索引。
  • explain 解读：重点看 type（ALL=全表扫描要优化）、key（实际用到的索引）、rows（扫描行数）、Extra（Using filesort/temporary 要优化）。
  • 常见优化：避免 SELECT *、避免函数包裹索引列、避免隐式类型转换、深分页用游标/子查询优化、N+1 查询改 JOIN 或预加载。

性能优化方法论 核心

  • 指标：QPS/TPS、响应时间（P50/P95/P99）、错误率、资源利用率（CPU/内存/IO）。
  • 优化顺序：先压测定位瓶颈（不是猜），再分层优化：应用代码 → 数据库 → 缓存 → 架构。
  • 应用层：慢查询日志、代码热点（Xdebug 分析）、减少重复计算、异步化耗时任务。
  • 数据库层：索引、分页、连接池、读写分离。
  • 压测工具：ab、wrk、JMeter；压测环境与生产配置尽量一致。
常见坑：没有数据支撑的「优化」是玄学；优化后必须做对比验证（压测前后数据）。

Web 安全加固 核心

  • SQL 注入：预处理参数化 + 最小权限数据库账号 + 严格过滤。
  • XSS：输出转义（htmlspecialchars）、CSP 头、HttpOnly Cookie。
  • CSRF：Token 校验（Laravel 自带）、SameSite Cookie、校验 Referer。
  • 文件上传：白名单校验类型/大小、重命名、禁止执行目录、用 OSS 存储。
  • 其他：SSRF（限制内网访问）、越权（垂直/水平，接口做资源属主校验）、敏感信息脱敏、HTTPS 强制。
为什么重要：安全是「1 和 0」——一个漏洞可能让整个系统归零；OWASP Top 10 是必读清单。

单元测试与接口测试 质量

  • PHPUnit 基础：断言、数据提供者、测试前后置（setUp/tearDown）。
  • 测试金字塔：单元测试（多）→ 接口测试（中）→ 端到端（少）。
  • 接口测试工具：Postman 集合 + 自动化 Runner；或 PHPUnit + Laravel 测试客户端。
  • 覆盖率目标：核心业务逻辑覆盖 70%+，不追求数字游戏。

1.4高级架构（第 7–9 月） 高并发 + 分布式 + 容器化 ▶

高并发架构设计 核心

是什么：从单体 → 分层 → 集群 → 微服务的演进，本质是「分流、缓存、异步、限流」八字方针。

  • 分层分流：Nginx 负载均衡（轮询/加权/IP Hash/一致性哈希）→ 应用集群无状态化 → 数据库读写分离。
  • 缓存：浏览器/CDN/Redis/本地缓存多级缓存，把热点请求挡在数据库之外。
  • 异步：消息队列削峰填谷（秒杀下单、短信、日志）；异步化不阻塞主流程。
  • 限流降级熔断：令牌桶/漏桶限流；非核心功能降级；下游异常熔断（Sentinel/自研）。
  • 分布式理论：CAP 定理（一致性/可用性/分区容错性三选二）、BASE 理论（最终一致）。
为什么重要：架构能力是区分中级与高级的分水岭，面试场景题（秒杀、热点）都考这些。

读写分离与分库分表 进阶

  • 读写分离：主库写、从库读，主从复制（binlog）同步；注意主从延迟（读不到刚写的数据 → 关键读走主库/半同步）。
  • 垂直拆分：按业务域拆库（用户库/订单库/商品库），降低单库压力。
  • 水平拆分：按分片键（如 user_id）hash/range 分表；中间件 ShardingSphere/MyCat 透明路由。
  • 拆分代价：跨分片 JOIN 变难、分布式事务变复杂、全局唯一 ID 需要（雪花算法）。

2.1入门篇（第 1–4 月） Kotlin + 组件 + UI ▶

Kotlin 语言核心 核心

是什么：Google 官方推荐语言，100% 兼容 Java，语法更简洁安全。与 Java 的最大区别：空安全、扩展函数、协程、数据类。

  • 空安全：类型默认非空；可空类型用 ?（String?），安全调用 ?. 、Elvis ?:、非空断言 !!（慎用）。
  • 集合高阶函数：map/filter/fold/groupBy/sortedBy/forEach 是日常主力，比 Java 循环更声明式。
  • 数据类：data class 自动生成 equals/hashCode/toString/copy，适合做 Model。
  • 扩展函数：给已有类加方法（如 fun String.isEmail()），不改变原类。
  • 协程入门：GlobalScope.launch（正式用 lifecycleScope/viewModelScope）+ suspend 挂起函数 + withContext(Dispatchers.IO) 切换线程。
  • 委托：by lazy 懒加载、by viewModels() 获取 ViewModel。

Activity 生命周期与启动模式 核心

是什么：Activity 是界面载体，生命周期是 Android 面试第一题，也是内存泄漏排查的基础。

  • 生命周期回调：onCreate（创建）→ onStart（可见）→ onResume（可交互）→ onPause（部分不可见）→ onStop（完全不可见）→ onDestroy（销毁）；后台被系统回收前走 onSaveInstanceState。
  • 四种启动模式：standard（默认，每启动新建）、singleTop（栈顶复用）、singleTask（栈内唯一，清其上）、singleInstance（独立任务栈，全局唯一，适合来电界面）。
  • onNewIntent：singleTop/singleTask 复用时会走此方法接收新 Intent。
  • 场景题：A 启动 B 时 A 走 onPause → B onCreate→onResume → A onStop；按返回键则 B onPause → A onRestart→onStart→onResume → B onStop→onDestroy。
常见坑：不要在 onPause 做耗时操作；旋转屏幕 Activity 重建（配置变更），数据用 ViewModel 或 onSaveInstanceState 保存。

Fragment 与生命周期 核心

  • Fragment 是 Activity 内的模块化界面，便于平板适配与导航管理。
  • 生命周期比 Activity 多 onAttach/onCreateView/onViewCreated/onDestroyView/onDetach；onViewCreated 后操作 view。
  • 通信方式：接口回调、ViewModel 共享、Fragment Result API（setFragmentResult）。
  • add 与 replace 区别：replace 会销毁旧 Fragment 视图；add 保留，配合 hide/show 切换。

布局与 UI 控件 核心

  • 布局类型：ConstraintLayout（首选，约束定位）、LinearLayout（线性）、FrameLayout（层叠）、RelativeLayout（相对，性能一般）。
  • 常用控件：TextView/EditText/Button/ImageView/RecyclerView/ScrollView/ViewPager2。
  • RecyclerView 三要素：Adapter（数据→视图）、LayoutManager（线性/网格/瀑布流）、ItemDecoration（分割线/间距）；ViewHolder 缓存复用是高性能关键。
  • dimens：dp（密度无关像素，布局）、sp（字号）、px（像素，不直接用）。

四大组件与数据存储 进阶

  • Service：后台执行（播放音乐/下载）；startService 与 bindService 两种启动方式；前台服务需通知（Android 8+）。
  • BroadcastReceiver：接收系统/应用广播（开机、网络变化）；静态注册（Manifest）与动态注册（registerReceiver，需注销）。
  • ContentProvider：跨应用数据共享（联系人、相册）；Android 10+ 分区存储限制直接读公共目录。
  • 存储方案：SharedPreferences（轻量键值）、Room/SQLite（结构化）、文件（内部/外部）、DataStore（SP 替代方案）。

2.2进阶篇（第 5–9 月） Jetpack + 网络 + 性能 ▶

Jetpack 全家桶 核心

  • ViewModel：持有 UI 数据，配置变更（旋转屏）后不销毁，通过 ViewModelStore 保存；绝不在 ViewModel 持有 Activity 引用（内存泄漏）。
  • LiveData：可观察数据，感知生命周期——只在 STARTED/RESUMED 状态回调观察者，自动避免更新已销毁 UI；observe 在活跃状态自动恢复接收。
  • DataBinding/ViewBinding：ViewBinding 编译期生成绑定类，替代 findViewById，空安全；DataBinding 支持 XML 绑定表达式（注意性能与可读性取舍）。
  • Navigation：导航图可视化管理 Fragment 切换、传参、返回栈；navController.navigate(R.id.action_a_to_b)。
  • WorkManager：保证式后台任务（上传/同步），兼容 Doze 模式；链式任务 workA.then(workB)。
  • Paging 3：分页加载列表，配合 RecyclerView + Flow；处理加载状态、重试、占位。

网络层：Retrofit + OkHttp + 协程 核心

是什么：Retrofit 是 REST 接口框架（注解声明接口），OkHttp 是底层 HTTP 客户端（连接池/拦截器），协程负责线程切换。

// Retrofit 接口 + 协程调用示例
interface ApiService {
    @GET("user/{id}")
    suspend fun getUser(@Path("id") id: Long): ApiResponse<User>
}
// 调用：viewModelScope.launch { val user = api.getUser(1) }
  • OkHttp 核心：连接复用（ConnectionPool）、超时管理、拦截器链（日志/Header/缓存/重试）、支持 HTTP/2。
  • 协程网络：suspend 函数自动切换 IO 线程（Retrofit 内置），无需手动 enqueue 回调，代码像同步一样顺序。
  • 错误处理：统一 try-catch + 密封类封装成功/错误状态；HTTP 错误、业务 code、网络异常三分。
  • JSON：Moshi/Gson/Kotlinx.serialization 反序列化，注意字段为 null 的兼容。

图片加载：Glide 原理 核心

  • 缓存三级：内存缓存（LruCache）→ 磁盘缓存 → 网络。
  • 生命周期感知：自动绑定 Activity/Fragment 生命周期，不可见时暂停加载。
  • Bitmap 复用：BitmapPool 复用内存，配合 inSampleSize 采样压缩，避免 OOM。
  • 占位/错误：placeholder / error / fallback；列表滚动中 skipMemoryCache 按需。
  • Coil：Kotlin 协程实现的新库，更轻量，Compose 项目常用。

线程与并发：Handler 与协程深入 核心

Handler 机制（面试必问）：Looper 负责从 MessageQueue 循环取消息，Handler 负责发送与处理消息，ThreadLocal 保证每个线程一个 Looper。

  • 主线程更新 UI：子线程不能直接改 UI（ViewRootImpl 校验），通过 Handler.post / runOnUiThread / 协程切主线程。
  • 内存泄漏：非静态内部类 Handler 持有外部 Activity → 消息未处理完 Activity 无法回收 → 用静态 Handler + 弱引用或 Lifecycle 绑定。
  • 协程深入：CoroutineScope + Dispatchers（Main/IO/Default）+ Job/Deferred + 结构化并发（取消传播）；withContext/async-await/coroutineScope。
  • 线程池：Executors 四种线程池与适用场景；Android 推荐协程替代大部分线程池。

依赖注入：Hilt 进阶

  • Hilt = Dagger 的 Android 封装：@HiltAndroidApp 应用类 + @AndroidEntryPoint 组件 + @Inject constructor 构造注入 + @Module/@Provides 提供第三方依赖。
  • 好处：解耦、便于单元测试（Mock）、作用域管理（@Singleton/@ActivityScoped）。

2.3精通篇（第 10–12 月） 架构 + 源码 + 性能优化 ▶

MVVM 架构实践 核心

是什么：MVVM = Model（数据/仓库）+ View（Activity/Fragment/XML）+ ViewModel（状态与业务逻辑，通过 LiveData/StateFlow 暴露）。

  • 单向数据流：View 事件 → ViewModel 方法 → 更新 State → View 观察刷新，避免双向纠缠。
  • 分层：UI 层（Activity/Fragment/Adapter）→ ViewModel 层（状态+用例）→ Repository 层（数据源聚合）→ Data 层（本地/远程）。
  • Flow vs LiveData：新项目推荐 StateFlow（协程友好、防抖），LiveData 用于 Java 或简单场景。
  • 状态管理：UI State 用 data class 封装（loading/data/error 三态），配合 sealed class 表达事件。

性能优化体系 核心

  • 启动优化：冷启动时间 = Application 初始化 + 首帧；方案：异步初始化、延迟初始化（App Startup）、启动器 Splash 秒开、避免首屏过度绘制。
  • 内存优化：LeakCanary 检测泄漏；Bitmap 用采样/复用；大图用 Glide 缩放；避免静态持有 Activity/Context；Profile 查看内存抖动（频繁创建对象）。
  • 卡顿优化：掉帧（vsync 16.6ms）根因是主线程耗时；用 Systrace/Perfetto 定位；列表卡顿查 Adapter 复用、嵌套滑动、过度绘制。
  • APK 瘦身：R8 压缩、资源混淆（AndResGuard）、按需拆分（App Bundle）、删除无用资源（lint 检查）。
  • 网络优化：缓存策略、图片 WebP、请求合并、DNS 优化、弱网重试。

自定义 View 与事件分发 核心

  • 自定义 View 三方法：onMeasure（测量尺寸）→ onLayout（摆放子 View）→ onDraw（绘制）；自定义属性 attrs.xml。
  • 事件分发：dispatchTouchEvent → onInterceptTouchEvent（ViewGroup）→ onTouchEvent 三级流转；从 Activity 往下分发，未消费回传。
  • 滑动冲突：内外层同时消费滑动（如 ScrollView 嵌套 RecyclerView）→ 通过 onInterceptTouchEvent 或 requestDisallowInterceptTouchEvent 解决。

组件化与模块化 进阶

  • 组件化：按业务拆模块（module），独立编译调试，通过路由（ARouter/自研）跨模块跳转。
  • 模块通信：接口下沉到公共层 + 依赖注入/路由；避免模块间直接依赖。
  • 插件化/热修复：原理是 ClassLoader 替换（dex 插桩），如 Tinker/RePlugin；了解原理即可，注意合规与稳定性。

Compose 与跨端视野 趋势

  • Compose：声明式 UI，Kotlin 函数描述界面，状态驱动重组；与 View 系统互补（互操作）。
  • 跨端：Flutter（Dart，自绘引擎）、React Native（JS 桥接）；uni-app（Vue 语法，多端编译）适合快速多端。
  • 取舍：原生性能与生态最好；跨端省成本；按团队与业务选型。

Android 中级开发面试详细总结

3.1基础必考题 生命周期 / Handler / 组件 ▶
高频Activity 的启动流程是怎样的？基础
考察点：系统机制理解。
参考答案要点：应用进程发起 startActivity → Instrumentation.execStartActivity → ActivityTaskManager（AMS 侧）校验并创建 ActivityRecord → 通知应用进程创建 Activity → 应用侧通过 ActivityThread 的 Handler（H.LAUNCH_ACTIVITY）→ Instrumentation.newActivity 反射创建 → Activity.attach → onCreate 等生命周期 → 添加到 DecorView 显示。
必考Handler 机制的原理？为什么主线程 Looper 不会退出？基础
考察点：消息循环模型。
参考答案要点：Looper.loop() 死循环从 MessageQueue.next() 取消息（无消息时阻塞在 nativePollOnce 的 epoll，不耗 CPU），取到后交给 Handler.dispatchMessage 处理。quitSafely 会退出循环。主线程 Looper 由 ActivityThread.main 中 prepareMainLooper 创建，进程常驻需要持续处理消息；「死循环不卡死」的关键是 next() 在无消息时休眠等待（epoll 唤醒），而非空转。
必考Service 的两种启动方式与区别？基础
考察点：四大组件。
参考答案要点：startService（独立启动，onStartCommand 处理任务，需 stopService 停止，与调用者无关）；bindService（绑定式，onBind 返回 Binder，可与调用者通信，调用者销毁自动解绑，解绑后销毁）；可先 start 再 bind，需同时 stop 与 unbind 才销毁。Android 8+ 后台启动 Service 受限，需前台服务。
高频RecyclerView 为什么比 ListView 高效？缓存机制？基础
考察点：列表性能。
参考答案要点：ViewHolder 复用避免重复 findViewById；四级缓存：mAttachedScrap（屏幕内复用）→ mCachedViews（默认 2 个，无需重建）→ mRecyclerPool（跨 Adapter 复用，需重绑定）→ 创建新 ViewHolder；配合局部刷新（notifyItemChanged）与 DiffUtil 精准更新；LayoutManager 负责测量布局，支持预取（Prefetch）。
高频如何避免 ANR？基础
考察点：主线程治理。
参考答案要点：触发条件：输入事件 5s、BroadcastReceiver 前台 10s/后台 60s、Service 前台 20s 未处理完。避免：耗时操作（网络/IO/大计算）全部移出主线程（协程/线程池）；避免主线程等待锁；广播中不做耗时；用 AsyncTask 已废弃，改协程；配合 StrictMode 检测主线程 IO。
高频如何保证多线程安全地更新 UI？基础
考察点：线程模型。
参考答案要点：Android UI 非线程安全，只能主线程更新。方式：View.post()、runOnUiThread、Handler.post、协程 withContext(Dispatchers.Main)；子线程只做数据准备，通过 LiveData/Flow 把结果回传主线程观察更新。
3.2进阶高频题 原理 / 优化 / 架构 ▶
进阶LiveData 的原理？与 StateFlow 的区别？进阶
考察点：Jetpack 原理。
参考答案要点：LiveData 内部用 LifecycleBoundObserver（实现 LifecycleEventObserver），根据宿主状态（STARTED/RESUMED）决定是否分发（shouldBeActive），销毁自动移除；setValue 必须在主线程，postValue 可子线程。StateFlow：基于协程 Flow 的状态容器，初始值必须有、支持防抖（distinctUntilChanged）、协程友好、不感知生命周期（需 repeatOnLifecycle）。LiveData 适合 Java 与简单场景，StateFlow 适合 Kotlin 新项目。
进阶协程的原理？为什么「挂起」不阻塞线程？进阶
考察点：并发机制。
参考答案要点：Kotlin 协程基于状态机（CPS 变换），suspend 函数被编译为带有 Continuation 的状态机对象；挂起 = 当前协程让出线程并保存状态（Continuation 的 resumeWith 续接），线程可以去执行别的任务；恢复 = 在指定 Dispatcher 上继续执行。所以挂起不占线程，本质是「回调扁平化 + 线程调度封装」。
进阶App 启动优化的完整方案？进阶
考察点：性能优化。
参考答案要点：（1）度量：adb 看 Displayed 时间 / 启动 trace；（2）Application 优化：异步初始化（线程池并行）、延迟初始化（首帧后）、App Startup 合并初始化器；（3）首屏优化：布局扁平化、减少过度绘制、用启动主题占位 + 冷启动秒开；（4）业务优化：首屏只加载必要数据、接口并行请求；（5）工具：Perfetto/Systrace 分析、字节码插桩统计初始化耗时。
进阶内存泄漏的常见场景与排查方法？进阶
考察点：内存治理。
参考答案要点：常见：静态变量持有 Activity/View、Handler 延迟消息、匿名内部类持有外部类、单例持有 Context（应用 Context 可）、未注销监听器/广播、Bitmap 未回收（现代 GC 自动）、协程未取消。排查：LeakCanary 自动定位；Android Profiler 看内存曲线（只增不减 = 泄漏）；MAT 分析 hprof 找 GC Root 引用链；Fix：作用域化对象、lifecycle 绑定、弱引用、及时取消。
进阶MVVM 相比 MVC/MVP 的优势？进阶
考察点：架构认知。
参考答案要点：MVC：View 与 Controller 耦合，Activity 又当 View 又当 Controller 易臃肿；MVP：Presenter 与 View 接口解耦，但接口爆炸、Presenter 持有 View 易泄漏；MVVM：ViewModel 不持有 View（通过 LiveData/Flow 观察），天然规避泄漏，数据驱动 UI，可测试性高（ViewModel 纯 Kotlin 可单测）；配合 Repository 层统一数据源。
进阶如何设计一个图片加载库？深水区
考察点：系统设计能力。
参考答案要点：核心模块：请求管理（统一入口 load(url)）、内存缓存（LruCache，大小按可用内存 1/8）、磁盘缓存（DiskLruCache，按图片 key）、网络加载（OkHttp + 流式解码）、Bitmap 采样（inSampleSize 按 target 尺寸）、线程调度（加载线程池 + 主线程回调）、生命周期绑定（宿主销毁暂停/取消）、复用（BitmapPool）；进阶：预加载、优先级、进度回调、图片变换。

场景列表滑动卡顿，你会如何排查？项目

4.1打包与上架准备 签名 / 混淆 / 渠道 ▶

签名机制与打包 核心

  • 为什么签名：保证 APK 完整性 + 标识开发者身份；同包名不同签名无法覆盖安装/升级。
  • V1/V2/V3 签名：V1 仅校验未修改文件（Android 7.0 以下）；V2 全文件校验（7.0+，快且安全）；V3 支持密钥轮换（9.0+）。新包建议 V2+V3。
  • 签名工具：Android Studio 可视化生成 keystore（JKS/PKCS12）；apksigner verify 校验签名；密钥必须安全备份（丢失=无法升级）。
  • 构建变体：debug/release + flavor（渠道包）；BuildConfig 区分环境地址。

混淆与代码安全 核心

  • R8：AGP 8+ 默认启用，集压缩、混淆、优化、脱糖于一体；minifyEnabled true。
  • 规则文件：keep 住被反射/注解/序列化使用的类（model、SDK 回调、WebView JS 接口）；第三方库自带 consumer proguard 规则。
  • 资源压缩：shrinkResources true 删除无用资源；注意动态引用（getIdentifier）需 keep。
  • 加固：上架前可选第三方加固（爱加密/梆梆/360），防逆向；敏感字符串不硬编码（加密存储）。

多渠道打包 进阶

  • 传统：gradle flavorDimensions 每渠道一个包（慢）。
  • 高效：Gradle 动态配置 + 打包后批量改 meta-data（美团瓦力/Walle 方案），一套包多渠道。
  • 渠道统计：SDK 读取 meta-data 上报，用于投放与运营分析。

各层职责详解 核心

  • 前端表现层：只负责「展示 + 交互」，不直接操作数据库；统一通过 API 客户端（封装 request）与后端通信；状态管理用 Pinia（用户态、全局配置）。
  • 接口业务层（PHP）：校验参数、编排业务（如「下单 = 扣库存 + 建订单 + 发消息」）、调用 AI 服务或数据库；输出统一 JSON。

设计要点 核心

  • 范式与冗余：核心表满足 3NF；读多场景允许冗余（如订单冗余商品名快照，防止商品改名影响历史订单）。
  • 索引：外键与高频查询列建索引；联合索引最左前缀；避免冗余索引。
  • 软删除：业务表加 deleted_at，避免物理删除丢失审计。
  • 时间字段：统一 DATETIME（UTC 存储、展示转本地）或时间戳；created_at/updated_at 自动维护。
  • 金额：用 DECIMAL(10,2) 或分存储（INT），禁用 float。
5.5AI 服务实战（Python + FastAPI） 搭建 / 流式 / 部署 ▶

FastAPI 服务骨架 核心

# main.py - FastAPI 流式 AI 接口
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import httpx

app = FastAPI()

@app.post("/v1/chat")
async def chat(req: dict):
    messages = req["messages"]
    async def gen():
        async with httpx.AsyncClient(timeout=60) as client:
            async with client.stream("POST", "https://api.llm/v1/chat/completions",
                json={"messages": messages, "stream": True}) as r:
                async for line in r.aiter_lines():
                    if line.startswith("data:"):
                        yield line[5:] + "\n"
    return StreamingResponse(gen(), media_type="text/event-stream")
  • 为什么 FastAPI：原生 async 高并发、Pydantic 自动校验与文档、轻量易部署。
  • 流式输出（SSE）：大模型回复长，流式逐字返回让用户体验好；前端用 EventSource 或 fetch 流式读取。
  • 安全：AI 服务只允许内网调用（PHP 服务间调用），做来源白名单 + 简单鉴权；用户输入做长度限制与敏感词过滤。
  • 部署：Uvicorn 多进程 + Nginx 反代；Docker 打包；日志与监控接入。
