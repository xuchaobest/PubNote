OC第 1 章 OC 基础语法

1.1 类与对象

OC 是 C 语言的超集，采用消息发送机制而非函数调用。@interface 声明接口，@implementation 实现。

// .h 文件
@interface Person : NSObject
@property (nonatomic, copy) NSString *name;
@property (nonatomic, assign) NSInteger age;
- (instancetype)initWithName:(NSString *)name age:(NSInteger)age;
- (void)sayHello;
@end

// .m 文件
@implementation Person
- (instancetype)initWithName:(NSString *)name age:(NSInteger)age {
    self = [super init];
    if (self) {
        _name = [name copy];
        _age = age;
    }
    return self;
}
- (void)sayHello {
    NSLog(@"Hello, I'm %@, %ld years old", self.name, (long)self.age);
}
@end
1.2 属性关键字
关键字作用默认
atomic / nonatomic原子性（线程安全）/ 非原子atomic
assign直接赋值，不改变引用计数基本类型默认
strong强引用，引用计数 +1对象默认
weak弱引用，不改变引用计数，对象释放后自动置 nil—
copy拷贝对象，常用于 NSString/Block—
readonly / readwrite只读 / 读写readwrite
面试高频atomic 只能保证 getter/setter 原子性，不能保证多线程安全（如遍历数组时被修改）。nonatomic 性能更好，iOS 开发中几乎都用 nonatomic。
1.3 分类（Category）与扩展（Extension）
维度CategoryExtension
位置独立 .h/.m 或 .m 中必须在 .m 文件中
添加属性只能声明，需 Runtime 关联对象实现可以添加私有属性
添加方法可以添加方法声明私有方法
命名有名字（如 NSString+Utils）匿名
实现必须有实现实现写在主 @implementation 中
注意Category 中如果实现了与原类同名的方法，会覆盖原方法（实际是方法列表中先被找到），且多个 Category 同名方法的执行顺序不确定（取决于编译顺序）。
1.4 协议（Protocol）

@end

OC第 2 章 内存管理

2.1 MRC 与 ARC

MRC（手动引用计数）：手动调用 retain/release/autorelease。ARC（自动引用计数）：编译器在编译时自动插入 retain/release，开发者通过 strong/weak/copy/assign 控制引用关系。

核心原则谁创建（alloc/new/copy/mutableCopy）谁释放；谁 retain 谁 release。ARC 下不能直接调用 retain/release/dealloc 中调用 [super dealloc]。
2.2 autoreleasepool
@autoreleasepool {
    for (int i = 0; i < 100000; i++) {
        NSString *str = [NSString stringWithFormat:@"%d", i];
        // 大量临时对象，在 pool 结束时统一释放
    }
}

autorelease 对象会被加入当前最近的 autoreleasepool，pool 销毁时统一 release。主线程的 RunLoop 在每次事件循环开始时创建 pool，结束时销毁。循环中创建大量临时对象时手动加 autoreleasepool 可降低内存峰值。

2.3 循环引用与解决

常见场景：self -> block -> self；self -> delegate -> self；NSTimer -> target -> self。

// Block 循环引用的标准解决：weak-strong dance
__weak typeof(self) weakSelf = self;
self.block = ^{
    __strong typeof(weakSelf) strongSelf = weakSelf;
    if (strongSelf) {
        [strongSelf doSomething];
    }
};

NSTimer 循环引用：用 weak proxy 中介对象（NSProxy 子类）打破强引用链，或用 iOS 10+ 的 block-based API。

// iOS 10+ block 方式（仍需注意 self 被 block 捕获）
__weak typeof(self) weakSelf = self;
[NSTimer scheduledTimerWithTimeInterval:1.0 repeats:YES block:^(NSTimer * _Nonnull timer) {
    [weakSelf tick];
}];
2.4 weak 实现原理

Runtime 维护一个 weak 表（hash 表），key 是对象地址，value 是指向该对象的 weak 指针地址列表。对象 dealloc 时，Runtime 遍历 weak 表，将所有指向该对象的 weak 指针置为 nil。

weak vs assign：assign 不自动置 nil，对象释放后变成野指针（EXC_BAD_ACCESS）；weak 自动置 nil，更安全。assign 用于基本类型，weak 用于对象。

OC第 3 章 Runtime（运行时）

3.1 消息发送机制

OC 的方法调用本质是消息发送：[receiver message] 编译为 objc_msgSend(receiver, @selector(message))。

objc_msgSend 流程： 1. 通过对象的 isa 指针找到类对象 2. 在类对象的方法缓存（cache_t）中查找 SEL 3. 缓存命中 → 直接调用 IMP 4. 缓存未命中 → 在类的方法列表（method_list_t）中查找 5. 找到 → 加入缓存，调用 IMP 6. 未找到 → 沿 superclass 链向上查找 7. 仍未找到 → 进入消息转发流程
3.2 消息转发三阶段
阶段1：动态方法解析 +resolveInstanceMethod: / +resolveClassMethod: → 可以动态添加方法实现 阶段2：快速转发 -forwardingTargetForSelector: → 返回一个能处理该消息的对象 阶段3：完整转发 -methodSignatureForSelector: 获取方法签名 -forwardInvocation: 手动处理 NSInvocation → 可以修改参数、选择目标、多对象分发
面试高频如果三阶段都不处理，最终调用 doesNotRecognizeSelector: 抛出异常（unrecognized selector sent to instance）。
3.3 方法交换（Method Swizzling）
#import 

@implementation UIViewController (Tracking)
+ (void)load {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        Class class = [self class];
        SEL originalSelector = @selector(viewWillAppear:);
        SEL swizzledSelector = @selector(track_viewWillAppear:);
        Method originalMethod = class_getInstanceMethod(class, originalSelector);
        Method swizzledMethod = class_getInstanceMethod(class, swizzledSelector);
        // 先尝试添加原方法，防止父类未实现
        BOOL didAddMethod = class_addMethod(class, originalSelector,
            method_getImplementation(swizzledMethod),
            method_getTypeEncoding(swizzledMethod));
        if (didAddMethod) {
            class_replaceMethod(class, swizzledSelector,
                method_getImplementation(originalMethod),
                method_getTypeEncoding(originalMethod));
        } else {
            method_exchangeImplementations(originalMethod, swizzledMethod);
        }
    });
}
- (void)track_viewWillAppear:(BOOL)animated {
    [self track_viewWillAppear:animated]; // 调用原方法
    NSLog(@"页面曝光: %@", NSStringFromClass([self class]));
}
@end
注意事项必须在 +load 中执行（保证尽早交换）；用 dispatch_once 保证线程安全；交换的方法必须调用原实现（除非故意替换）；避免交换父类方法影响所有子类。
3.4 关联对象（Associated Objects）
#import 

static const void *kNameKey = &kNameKey;

- (void)setName:(NSString *)name {
    objc_setAssociatedObject(self, kNameKey, name, OBJC_ASSOCIATION_COPY_NONATOMIC);
}
- (NSString *)name {
    return objc_getAssociatedObject(self, kNameKey);
}

关联对象策略：OBJC_ASSOCIATION_ASSIGN、RETAIN_NONATOMIC、COPY_NONATOMIC、RETAIN、COPY。常用于 Category 中添加属性。

3.5 isa 指针与类的结构
instance 对象 └─ isa → class 对象（类对象） ├─ isa → metaclass（元类对象） ├─ superclass → 父类对象 ├─ method_list → 实例方法列表 ├─ cache → 方法缓存 └─ ivar_list → 成员变量列表 instance 的方法存在 class 中 class 的方法（类方法）存在 metaclass 中 metaclass 的 isa 指向根元类（NSObject metaclass） 根元类的 superclass 指向 NSObject class（类对象） NSObject class 的 superclass = nil

OC第 4 章 RunLoop

4.1 RunLoop 基础

RunLoop 是一个事件循环，保持线程存活并处理事件。主线程默认开启 RunLoop，子线程需要手动获取并运行。

模式（Mode）说明
NSDefaultRunLoopMode默认模式，处理大部分事件
UITrackingRunLoopMode滚动时的模式，优先级高
NSRunLoopCommonModes默认模式 + 滚动模式的集合
经典问题NSTimer 在 UIScrollView 滚动时不触发，因为 RunLoop 切换到了 UITrackingRunLoopMode，而 timer 默认在 default mode。解决：将 timer 添加到 NSRunLoopCommonModes。
4.2 RunLoop 事件源
  • Source0：非基于 port 的事件，如 UIEvent、performSelector
  • Source1：基于 port 的事件，如进程间通信、系统事件
  • Timer：NSTimer、dispatch_source_t timer
  • Observer：监听 RunLoop 状态（进入、休眠、唤醒、退出）
4.3 RunLoop 应用场景
  1. 保持线程存活：子线程中开启 RunLoop，实现常驻线程（如 AFNetworking 的网络线程）
  2. 监控卡顿：添加 Observer 监听 RunLoop 进入休眠前的状态，超时则判定卡顿
  3. 异步绘制：在 RunLoop 空闲时（BeforeWaiting）执行绘制任务
  4. AutoreleasePool：RunLoop 管理 autoreleasepool 的创建和销毁
  5. 事件响应：触摸事件、手势识别都依赖 RunLoop 分发
4.4 卡顿监控实现
static void runLoopObserverCallBack(CFRunLoopObserverRef observer,
    CFRunLoopActivity activity, void *info) {
    MyMonitor *monitor = (__bridge MyMonitor *)info;
    monitor->currentActivity = activity;
    dispatch_semaphore_signal(monitor->semaphore);
}

- (void)startMonitor {
    CFRunLoopObserverContext context = {0, (__bridge void *)self, NULL, NULL};
    CFRunLoopObserverRef observer = CFRunLoopObserverCreate(
        kCFAllocatorDefault, kCFRunLoopAllActivities, YES, 0,
        &runLoopObserverCallBack, &context);
    CFRunLoopAddObserver(CFRunLoopGetMain(), observer, kCFRunLoopCommonModes);

    dispatch_async(dispatch_get_global_queue(0, 0), ^{
        while (YES) {
            // 等待 50ms，超时则认为可能卡顿
            long result = dispatch_semaphore_wait(self.semaphore,
                dispatch_time(DISPATCH_TIME_NOW, 50 * NSEC_PER_MSEC));
            if (result != 0) {
                if (self.currentActivity == kCFRunLoopBeforeSources ||
                    self.currentActivity == kCFRunLoopAfterWaiting) {
                    NSLog(@"检测到卡顿！");
                }
            }
        }
    });
}

OC第 5 章 Block

5.1 Block 的三种类型
类型存储区域条件
NSGlobalBlock全局区（数据段）不捕获外部变量，或只捕获全局/静态变量
NSStackBlock栈区捕获了局部变量，在 MRC 下存在；ARC 下通常自动 copy 到堆
NSMallocBlock堆区StackBlock 调用 copy 后，或 Block 作为属性被 strong/copy 修饰
ARC 下大多数情况下编译器会自动将 StackBlock copy 到堆上，开发者感知不到三种类型的区别。但理解底层对面试很重要。
5.2 Block 捕获变量
int globalVar = 10;
static int staticVar = 20;

void (^block)(void) = ^{
    // 全局变量、静态变量：直接访问，可修改
    globalVar = 100;
    staticVar = 200;
    // 局部变量：值捕获，不可修改（编译报错）
    // localVar = 300; // ❌
    NSLog(@"localVar = %d", localVar); // ✅ 只读访问
};

// __block 修饰的变量：引用捕获，可修改
__block int blockVar = 30;
void (^block2)(void) = ^{
    blockVar = 300; // ✅
};
__block 原理编译器将 __block 变量包装成一个结构体（__Block_byref_var_0），包含 forwarding 指针和变量值。Block 捕获的是这个结构体的指针，因此可以修改原始变量。
5.3 Block 循环引用

self 强引用 block（属性），block 内强引用 self → 循环引用。解决：weak-strong dance（见第 2 章）。

延迟调用场景如果 block 内需要异步延迟执行，weakSelf 可能在执行前被释放。此时在 block 内用 strongSelf 持有，保证 block 执行期间 self 不被释放。

OC第 6 章 KVO / KVC

6.1 KVO 实现原理

KVO（Key-Value Observing）基于 Runtime 实现。当对一个对象的属性添加观察者时，Runtime 动态创建一个该类的子类（NSKVONotifying_OriginalClass），重写被观察属性的 setter 方法，在 setter 中调用 willChangeValueForKey: 和 didChangeValueForKey:，通知观察者。

添加观察者后： Person 对象的 isa → 从 Person 类变为 NSKVONotifying_Person 类 NSKVONotifying_Person 重写 setName: - willChangeValueForKey:@"name" - 调用父类 setName:（真正赋值） - didChangeValueForKey:@"name" → 通知观察者 NSKVONotifying_Person 还重写： - class：返回原类名（隐藏子类存在） - dealloc：释放资源 - _isKVOA：返回 YES
6.2 KVO 使用
// 添加观察
[self.person addObserver:self forKeyPath:@"name"
    options:NSKeyValueObservingOptionNew | NSKeyValueObservingOptionOld
    context:nil];

// 接收通知
- (void)observeValueForKeyPath:(NSString *)keyPath
                      ofObject:(id)object
                        change:(NSDictionary *)change
                       context:(void *)context {
    if ([keyPath isEqualToString:@"name"]) {
        NSLog(@"name changed: %@ -> %@",
            change[NSKeyValueChangeOldKey], change[NSKeyValueChangeNewKey]);
    }
}

// 移除观察（必须，否则崩溃）
- (void)dealloc {
    [self.person removeObserver:self forKeyPath:@"name"];
}
注意必须移除观察者，否则对象释放后再收到通知会崩溃。手动调用 setter 才会触发 KVO，直接修改成员变量（_name = xxx）不会触发。
6.3 KVC

KVC（Key-Value Coding）通过字符串 key 访问属性。setValue:forKey: 查找顺序：setKey: → _setKey: → 访问 _key → _isKey → key → isKey → setValue:forUndefinedKey:。

[person setValue:@"Tom" forKey:@"name"];
NSString *name = [person valueForKey:@"name"];

// 字典转模型
NSDictionary *dict = @{@"name": @"Tom", @"age": @25};
[person setValuesForKeysWithDictionary:dict];

// 集合操作
NSArray *ages = [people valueForKeyPath:@"@avg.age"]; // 平均年龄

OC第 7 章 多线程

7.1 GCD 核心概念
队列类型说明
主队列（main）串行，主线程执行，UI 操作必须在这里
全局队列（global）并发，4 个优先级（default/userInitiated/utility/background）
自定义串行队列串行，FIFO，常用于资源保护或任务顺序执行
自定义并发队列并发，可用于多任务并行执行
// 异步回到主线程
dispatch_async(dispatch_get_global_queue(0, 0), ^{
    // 耗时操作
    dispatch_async(dispatch_get_main_queue(), ^{
        // 更新 UI
    });
});

// 一次性执行（单例）
+ (instancetype)sharedInstance {
    static id instance;
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        instance = [[self alloc] init];
    });
    return instance;
}

// 延迟执行
dispatch_after(dispatch_time(DISPATCH_TIME_NOW, (int64_t)(2.0 * NSEC_PER_SEC)),
    dispatch_get_main_queue(), ^{
    NSLog(@"2秒后执行");
});

// 队列组（等待多个异步任务完成）
dispatch_group_t group = dispatch_group_create();
dispatch_group_async(group, queue, ^{ /* task1 */ });
dispatch_group_async(group, queue, ^{ /* task2 */ });
dispatch_group_notify(group, dispatch_get_main_queue(), ^{
    NSLog(@"所有任务完成");
});
7.2 线程同步与锁
锁性能特点
@synchronized低语法简单，自动释放锁，性能差
NSLock中Foundation 层，lock/unlock 配对
dispatch_semaphore高GCD 信号量，性能最好
pthread_mutex高C 语言级，性能好

// dispatch_semaphore 实现线程安全
dispatch_semaphore_t semaphore = dispatch_semaphore_create(1);
- (void)setName:(NSString *)name {
    dispatch_semaphore_wait(semaphore, DISPATCH_TIME_FOREVER);
    _name = name;
    dispatch_semaphore_signal(semaphore);
}

// 多读单写（barrier）
dispatch_queue_t queue = dispatch_queue_create("com.example.rw", DISPATCH_QUEUE_CONCURRENT);
- (id)read {
    __block id result;
    dispatch_sync(queue, ^{ result = self.data; });
    return result;
}
- (void)write:(id)data {
    dispatch_barrier_async(queue, ^{ self.data = data; });
}
7.3 NSOperation & NSOperationQueue

NSOperation 是 GCD 的 OC 封装，支持：依赖（addDependency）、优先级、取消、KVO 观察状态、最大并发数。

NSOperationQueue *queue = [[NSOperationQueue alloc] init];
queue.maxConcurrentOperationCount = 2;

NSBlockOperation *op1 = [NSBlockOperation blockOperationWithBlock:^{
    NSLog(@"任务1");
}];
NSBlockOperation *op2 = [NSBlockOperation blockOperationWithBlock:^{
    NSLog(@"任务2（依赖任务1完成）");
}];
[op2 addDependency:op1]; // op2 等 op1 完成
[queue addOperations:@[op1, op2] waitUntilFinished:NO];

OC第 8 章 性能优化

8.1 启动优化

启动阶段：pre-main（dyld 加载动态库、rebase/binding、ObjC 初始化、+load）→ main（UIApplicationMain、首屏渲染）。

  • 减少 +load 方法：将 +load 中的逻辑移到 +initialize 或首屏后
  • 减少动态库：合并动态库，Apple 建议少于 6 个
  • 懒加载：非首屏页面延迟加载
  • 首屏简化：减少首屏视图层级和计算
  • 二进制重排：通过 Order File 减少缺页中断（Page Fault）
8.2 卡顿优化

屏幕刷新率 60fps，每帧 16.7ms。主线程在 16.7ms 内未完成布局和绘制就会掉帧。

  • 异步绘制：将文本、图片绘制放到子线程（YYAsyncLayer、AsyncDisplayKit）
  • 减少离屏渲染：避免 cornerRadius+maskToBounds 同时使用大量视图；用预渲染图片替代
  • 减少视图层级：扁平化视图结构，减少约束计算
  • 缓存：行高缓存、Cell 高度预计算、图片缓存
  • 滑动优化：RunLoop 空闲时加载图片，避免滑动时同步解码
8.3 内存优化
  • 用 Instruments（Leaks/Allocations）检测内存泄漏和循环引用
  • 大图压缩：解码后尺寸远大于显示尺寸时，先缩放再解码
  • 列表图片使用 NSCache 管理，收到内存警告时清理
  • autoreleasepool 控制大循环中的临时对象
  • WKWebView 替代 UIWebView（内存占用大幅降低）
8.4 离屏渲染

离屏渲染是指 GPU 在当前屏幕缓冲区之外开辟新的缓冲区进行渲染，然后再合成到屏幕。会导致性能损耗。

触发离屏渲染的操作：cornerRadius + masksToBounds（部分情况）、shadow（阴影）、shouldRasterize（光栅化）、mask（遮罩）、allowsEdgeAntialiasing。

优化圆角：用贝塞尔曲线绘制圆形图片（Core Graphics），或让服务端返回圆形/圆角图片，避免大量离屏渲染。

OC第 9 章 架构设计

9.1 MVC / MVVM / VIPER 对比
架构分层优点缺点

说一下 OC 的消息发送机制和消息转发流程。
objc_msgSend 通过 isa 找类 → 查缓存 → 查方法列表 → 沿父类链查找 → 都没找到进入消息转发。转发三阶段：①动态方法解析（resolveInstanceMethod: 可动态添加方法）②快速转发（forwardingTargetForSelector: 返回替代对象）③完整转发（methodSignatureForSelector: 获取签名 + forwardInvocation: 处理 NSInvocation）。都不处理则抛 unrecognized selector 异常。
Runtime 有哪些实际应用场景？
①Method Swizzling 埋点/无痕埋点 ②关联对象给 Category 添加属性 ③动态添加方法（@dynamic 属性、JSPatch 热修复）④字典转模型（KVC + Runtime 获取属性列表）⑤获取类的所有属性/方法/成员变量 ⑥KVO 底层实现 ⑦消息转发实现多代理、安全调用。
Block 为什么用 copy 而不是 strong？
Block 默认创建在栈上（NSStackBlock），栈上的 Block 在函数返回后会被销毁。用 copy 会将 Block 从栈复制到堆上（NSMallocBlock），堆上的 Block 生命周期由引用计数管理。用 strong 修饰时，ARC 下编译器也会自动 copy，但历史上 MRC 时期必须用 copy，所以习惯上 Block 属性用 copy。
__block 和 __weak 的区别？
__block 修饰的变量在 Block 内可以被修改（引用捕获，编译器包装成结构体），但会被 Block 强引用，可能导致循环引用。__weak 修饰的变量是弱引用，不增加引用计数，对象释放后自动置 nil，用于打破循环引用。两者用途不同：__block 解决"修改变量"，__weak 解决"循环引用"。
RunLoop 和线程的关系？怎么实现一个常驻线程？
RunLoop 和线程一一对应，主线程默认开启，子线程需要手动获取并运行。常驻线程实现：在子线程中获取 RunLoop，添加一个 Source/Timer（保证 RunLoop 有事件源，不会立即退出），然后调用 run 方法。注意：如果 RunLoop 没有任何 Source/Timer，调用 run 会立即返回。AFNetworking 就是用常驻线程处理网络回调。
NSTimer 为什么会导致循环引用？怎么解决？
NSTimer 会强引用 target（self），而 self 通常又强引用 timer（作为属性），形成循环引用。解决方案：①用 weak proxy（NSProxy 子类）作为 target 中介，proxy 弱引用 self ②iOS 10+ 用 block-based API + weakSelf ③在 viewWillDisappear 时 invalidate timer。注意 invalidate 必须在创建 timer 的线程调用。
atomic 是线程安全的吗？
atomic 只保证 getter/setter 的原子性（加锁防止读写同时进行），但不保证整体线程安全。例如数组属性 atomic 只保证赋值和获取是原子的，但多线程同时调用 addObject: 仍可能崩溃。线程安全需要开发者自己加锁或使用串行队列。
iOS 中怎么检测内存泄漏？
①Instruments Leaks 工具 ②Instruments Allocations 看对象是否该释放未释放 ③FBRetainCycleDetector（Facebook 开源，运行时检测循环引用）④MLeaksFinder（自动检测 UIViewController 泄漏）⑤dealloc 中加日志看是否调用 ⑥Xcode Memory Graph Debugger（可视化引用关系）。
说一下 iOS 启动优化的思路和具体手段。
分 pre-main 和 main 两阶段。pre-main：减少动态库数量（合并）、减少 +load 方法（移到 +initialize）、减少 rebase/binding（减少 OC 类/分类/C++ 静态构造函数）。main：延迟非首屏初始化、首屏视图层级简化、数据预加载、使用 xib/storyboard 减少代码创建。进阶：二进制重排（Order File）减少 Page Fault，可通过 clang -fsanitize-coverage 收集函数调用顺序。
离屏渲染是什么？哪些情况会触发？怎么优化？
离屏渲染是 GPU 在当前屏幕缓冲区外开辟新缓冲区渲染再合成，会导致性能损耗。触发：cornerRadius+masksToBounds（叠加裁剪时）、shadow 阴影、mask 遮罩、shouldRasterize 光栅化、allowsEdgeAntialiasing。优化：圆角用 Core Graphics 预绘制圆形图片、阴影用 shadowPath 指定路径、减少光栅化使用、Instruments Core Animation 勾选 Color Offscreen-Rendered Yellow 检测。

Swift第 18 章 Swift 资深面试题库

struct 和 class 的区别？什么时候用 struct？
struct 是值类型（赋值拷贝、栈分配、无继承、不需要 ARC），class 是引用类型（赋值引用、堆分配、支持继承、ARC 管理）。Swift 优先用 struct，因为值类型更安全（无共享状态、无循环引用）、性能更好（栈分配）。需要继承、引用语义、身份标识（===比较）、deinit 时用 class。SwiftUI 中所有 View 都是 struct。
说一下 Swift 的写时复制（COW）机制。
值类型赋值时不立即拷贝底层存储，而是共享。只有当修改发生时才真正拷贝。Array/Dictionary/String 都实现了 COW。自定义 struct 实现 COW 用 isKnownUniquelyReferenced 检查引用是否唯一，不唯一时才拷贝。COW 大幅提升了值类型在大量传递时的性能。
@StateObject 和 @ObservedObject 的区别？
@StateObject 由视图拥有，SwiftUI 保证只创建一次（视图刷新时不会重新初始化），用于在视图内部创建 ObservableObject。@ObservedObject 由外部注入，视图不拥有，每次视图刷新可能重新赋值。如果在视图内部创建 ObservableObject 必须用 @StateObject，否则会被反复创建导致状态丢失。
Actor 是怎么保证线程安全的？和锁有什么区别？
Actor 通过隔离（isolation）保证同一时间只有一个执行流访问其可变状态。编译器在编译期强制所有外部访问必须 await（异步排队），从根源上消除数据竞争。和锁的区别：锁是运行时机制，容易忘记加锁/死锁；Actor 是编译期保证，开发者无法绕过。Actor 内部方法是同步执行的，外部调用自动排队。@MainActor 是特殊的 Actor，绑定主线程。
some 和 any 的区别？
some（不透明类型）：编译器知道具体类型，同一函数返回类型固定，调用方不知道但编译器知道，零开销。any（存在类型）：运行时才确定具体类型，有性能开销（装箱、动态派发），用于需要存储不同类型的集合（如 [any View]）。Swift 5.7 后 any 必须显式标注。优先用 some，只有需要异构集合时才用 any。
SwiftUI 的视图刷新机制是怎样的？
SwiftUI 是声明式框架，当 @State/@Published 等状态变化时，视图的 body 被重新计算，生成新的视图树，SwiftUI diff 新旧视图树，只更新变化的部分。优化手段：提取子视图为独立 struct（值类型语义，SwiftUI 可判断是否需要刷新）、遵循 Equatable 自定义比较、使用 EquatableView、LazyVStack 懒加载、避免在 body 中做复杂计算。
Swift 的错误处理机制有哪些？
①throws/do-catch/try：可恢复错误 ②Result 类型：异步回调中传递结果 ③try?：错误转为可选型 ④try!：强制解包，错误则崩溃 ⑤assert/precondition：调试/发布断言 ⑥fatalError：不可恢复错误。Swift Concurrency 中 async throws 函数用 try await 调用。
怎么理解 @escaping 和 @autoclosure？
@escaping 标记逃逸闭包：闭包在函数返回后才执行（如网络回调），需要显式标记，且会捕获 self 可能导致循环引用。非逃逸闭包在函数返回前执行完，不允许存储。@autoclosure 自动将表达式包装成无参数闭包，延迟执行（如 && 的短路求值、assert 的条件），避免表达式在不需要时被计算。

Flutter第 25 章 Flutter 面试题库

说一下 Flutter 的三棵树和渲染流程。
Widget 树（不可变配置）→ Element 树（Widget 实例，持有 BuildContext）→ RenderObject 树（布局绘制）。流程：Widget build → inflateWidget 创建 Element → Element 创建/更新 RenderObject → RenderObject 执行 layout（约束传递）→ paint（绘制到 Layer）→ composite（合成）→ 上屏。setState 标记 Element dirty，下一帧重建 Widget，diff 后更新 RenderObject。
StatefulWidget 的生命周期？
createState → initState（一次，可访问 context 但不能用 async gap）→ didChangeDependencies（依赖变化时）→ build → didUpdateWidget（父 Widget 重建时）→ setState → deactivate（暂时移除）→ dispose（永久移除）。build 可能多次调用，initState/dispose 只调用一次。
Flutter 为什么性能好？和 React Native 有什么区别？
Flutter 自绘引擎（Skia/Impeller），不依赖原生控件，直接渲染到 GPU，避免 JS Bridge 通信开销。React Native 通过 JS Bridge 调用原生控件，有通信开销。Flutter 是 AOT 编译为原生代码，RN 是 JIT（开发）/AOT（发布）。Flutter 一致性更好（各平台 UI 一致），RN 更接近原生体验。
怎么优化 Flutter 列表性能？
①用 ListView.builder/SliverList 懒加载 ②itemExtent 固定行高避免动态计算 ③const 构造函数减少重建 ④图片用 cached_network_image + cacheWidth ⑤避免在 itemBuilder 中做重计算（提前算好）⑥RepaintBoundary 隔离 ⑦大列表用 CustomScrollView + Slivers。
BuildContext 是什么？为什么不能跨异步使用？
BuildContext 是 Element 的抽象，代表 Widget 在树中的位置。异步操作后 Element 可能已被移除（页面销毁），此时使用 context 会访问已失效的 Element，导致崩溃。Flutter 3.7+ 有 lint 警告。解决：异步前判断 if (!mounted) return;，或在异步前获取需要的值（如 Navigator）。

    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }

function auth(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'No token' });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
}

后端第 32 章 后端面试题库

Node.js 事件循环机制？setTimeout、setImmediate、process.nextTick、Promise 的执行顺序？
Node 事件循环基于 libuv，6 个阶段：timers → pending → idle/prepare → poll → check → close。microtask（nextTick + Promise）在每个阶段切换时执行。优先级：process.nextTick > Promise.then > setTimeout(0) > setImmediate。nextTick 在当前操作完成后立即执行，Promise 在 nextTick 之后，setTimeout 进入 timers 阶段，setImmediate 进入 check 阶段。
CommonJS 和 ES Module 的区别？
CJS 是同步运行时加载，值拷贝（基本类型）/引用（对象），require 动态执行，有 __dirname。ESM 是异步静态分析加载，实时绑定（引用），import 静态声明（也支持动态 import()），支持 Tree-shaking，无 __dirname（用 import.meta.url）。CJS 的 this 指向 module.exports，ESM 中 this 为 undefined。Node.js 中 .cjs 用 CJS，.mjs 用 ESM，package.json 的 type 字段决定默认。
PostgreSQL 索引有哪些类型？怎么优化慢查询？
索引类型：B-tree（默认，等值/范围/排序）、Hash（仅等值）、GIN（数组/JSONB/全文）、GiST（地理空间/全文）、BRIN（超大表）。优化慢查询：①EXPLAIN ANALYZE 看执行计划 ②确保查询条件走索引 ③避免函数包裹索引列、隐式类型转换、LIKE '%xxx' ④复合索引遵循最左前缀 ⑤覆盖索引避免回表 ⑥大表分页用游标替代 OFFSET ⑦定期 ANALYZE 更新统计信息。
怎么防止 SQL 注入？
①参数化查询（$1 占位符，驱动自动转义）②禁止字符串拼接 SQL ③ORM（Prisma/Sequelize）默认参数化 ④输入校验和白名单 ⑤最小权限原则（数据库账号只给必要权限）⑥WAF 拦截。永远不要信任用户输入，即使是内部系统。
JWT 的原理和优缺点？怎么处理登出？
JWT 由 header.payload.signature 三部分组成，服务端用密钥签名，客户端存储，请求时带在 Authorization 头。优点：无状态、服务端不需存 session、跨服务共享。缺点：无法主动失效、payload 不能存敏感信息（base64 非加密）、token 泄露风险。登出方案：①短期 access token + 长期 refresh token（refresh 存数据库可撤销）②黑名单（Redis 存已失效 token，过期自动清除）③版本号（用户表 token_version，JWT 中携带，修改密码时版本+1）。
云函数和云托管的区别？怎么选？
云函数（SCF）是事件驱动的无服务器函数，按需计费，有冷启动，适合短任务、事件触发、定时任务。云托管是容器化部署，常驻进程，无冷启动，支持长连接/WebSocket/任意框架，适合需要持续运行的服务。选择：简单 API/定时任务/微信小程序后端用云函数；复杂业务/长连接/需要自定义运行时用云托管。冷启动优化：预置并发、减少依赖体积、保持函数轻量。
怎么设计一个高并发的秒杀系统？
①前端限流（按钮置灰、验证码）②CDN 静态化页面③Nginx 限流（limit_req）④Redis 预减库存（原子操作 DECR，避免超卖）⑤消息队列削峰（Kafka/RabbitMQ，异步下单）⑥数据库乐观锁/悲观锁防超卖⑦分布式锁（Redis SETNX）⑧分库分表⑨兜底：降级、熔断、限流。核心思路：将请求挡在前面，异步处理，最终一致性。
