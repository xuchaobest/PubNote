前言 & 学习路线

为什么移动端开发者要学运维

作为移动端开发者，你可能专注于 Flutter、Swift、React Native 等前端技术，但在独立开发、创业项目或中小团队中，你往往需要同时承担后端开发、部署、运维的全链路工作。掌握运维能力能让你：

  • 独立完成全栈项目：从移动端到后端部署上线，全程一人搞定
  • 降低沟通成本：和运维团队沟通时更专业，快速定位问题
  • 提升技术竞争力：成为懂运维的移动端开发者，职场差异化优势明显
  • 更好地使用 CloudBase：理解底层运维原理，最大化利用云开发能力

整体学习路线图

💡 学习建议

按照「基础 → CloudBase 实战 → 通用运维技术 → 进阶架构」的顺序学习，边学边练，每学完一个章节就在自己的项目中实践。

  1. 基础阶段：Linux 命令 + Shell 脚本 + 网络基础（2周）
  2. 核心阶段：CloudBase 运维全流程 + Node.js 服务运维（3周）
  3. 进阶阶段：Docker 容器化 + CI/CD 自动化 + 监控告警（3周）
  4. 拔高阶段：K8s 基础 + 高可用架构 + 安全合规（选学，2周）

CloudBase 与运维的关系

腾讯云 CloudBase 是 Serverless 化的云开发平台，底层帮你屏蔽了大部分服务器运维工作，但这并不代表你不需要懂运维：

  • 云函数的性能调优、超时配置、内存设置需要运维思维
  • 数据库索引优化、存储容量管控属于运维范畴
  • 日志排查、问题定位依赖运维排查思路
  • 成本控制、资源配额管理是运维核心能力
  • 从 CloudBase 过渡到自建服务器，运维能力是必经之路

Linux 系统基础认知

1.1 发行版选择

发行版 特点 适用场景

文件系统与权限管理

3.1 权限说明

Linux 文件权限分为三组：所有者(u)、所属组(g)、其他用户(o)，每组有读(r)、写(w)、执行(x)三种权限。

# 示例：-rwxr-xr--
# 第一位：文件类型(-文件 d目录 l链接)
# 前三位：所有者权限 rwx
# 中三位：所属组权限 r-x
# 后三位：其他用户权限 r--

# 数字表示法：r=4, w=2, x=1
chmod 755 filename   # rwxr-xr-x
chmod 644 filename   # rw-r--r--
chmod +x filename    # 添加执行权限

# 更改所有者
chown user:group filename
chown -R user:group dirname
⚠️ 安全提醒

永远不要给文件 777 权限，这是极其危险的操作，会导致任意用户都可以修改执行文件。

运维常用脚本实战

3.1 日志清理脚本

#!/bin/bash
# 清理7天前的日志文件
LOG_DIR="/var/log/myapp"
DAYS=7

find $LOG_DIR -name "*.log" -mtime +$DAYS -delete
echo "[$(date)] 已清理 $LOG_DIR 下 $DAYS 天前的日志" >> /var/log/clean.log

3.2 服务健康检查

#!/bin/bash
# 检查Node服务是否存活
URL="http://localhost:3000/health"
RESPONSE=$(curl -s -o /dev/null -w "%{http_code}" $URL)

if [ $RESPONSE -ne 200 ]; then
    echo "服务异常，状态码：$RESPONSE，正在重启..."
    systemctl restart node-app
    echo "[$(date)] 服务已重启" >> /var/log/service-check.log
fi

第三章：CloudBase Node.js 运维实战

云函数部署与版本管理

1.1 本地开发与部署流程

作为移动端开发者，你可以使用 CloudBase CLI 工具进行云函数的部署与管理：

# 安装 CLI
npm install -g @cloudbase/cli

# 登录
tcb login

# 初始化项目
tcb init

# 部署单个云函数
tcb functions:deploy myFunction

# 部署全部云函数
tcb functions:deploy

# 查看云函数列表
tcb functions:list

1.2 版本与别名管理

云函数版本管理是运维核心能力，用于灰度发布和回滚：

# 发布版本
tcb functions:publish myFunction --desc "v1.0.0 正式版"

# 创建别名（测试环境指向$latest，正式环境指向固定版本）
tcb functions:create-alias myFunction --name prod --version 1

# 更新别名
tcb functions:update-alias myFunction --name prod --version 2

# 回滚版本
tcb functions:update-alias myFunction --name prod --version 1
💡 最佳实践

生产环境务必使用别名指向固定版本，不要直接使用 $latest。每次发布新版本后，先将 test 别名指向新版本验证，通过后再切换 prod 别名。

环境变量与配置管理

2.1 云函数环境变量

敏感配置（数据库密码、API密钥）不要写死在代码里，通过环境变量注入：

# 云函数中读取环境变量
const dbHost = process.env.DB_HOST;
const apiKey = process.env.API_KEY;

# CLI 设置环境变量
tcb functions:config set myFunction DB_HOST=127.0.0.1 API_KEY=xxx

# 查看环境变量
tcb functions:config get myFunction

2.2 多环境隔离

CloudBase 支持多环境，建议至少创建三套环境：

  • dev 环境：开发调试用，可随意修改
  • test 环境：测试验证用，保持稳定
  • prod 环境：生产环境，严格管控

日志查询与问题排查

3.1 日志查询方法

# CLI 查询日志
tcb functions:log myFunction --limit 100

# 查询错误日志
tcb functions:log myFunction --level error

# 按时间范围查询
tcb functions:log myFunction --startTime "2024-01-01 00:00:00" --endTime "2024-01-02 00:00:00"

3.2 常见问题排查思路

  1. 函数执行超时：检查是否有异步操作未结束、数据库查询慢、外部接口超时
  2. 内存溢出：大文件处理、内存泄漏，适当调高内存配置
  3. 依赖缺失：本地能运行线上报错，检查 package.json 依赖是否完整
  4. 权限不足：云函数角色权限，检查是否开通对应服务访问权限

性能监控与告警配置

4.1 核心监控指标

指标 说明 告警阈值建议
调用次数 函数调用总量 突增突降超过50%
错误率 调用失败占比 持续高于1%
平均耗时 函数执行时长 超过超时时间的80%
内存使用 运行内存峰值 超过配置内存的80%

4.2 告警配置

在 CloudBase 控制台 → 监控告警 → 告警策略中配置：

  • 支持邮件、短信、微信、企业微信等通知渠道
  • 关键指标（错误率、超时）必须配置告警
  • 避免告警风暴，设置合理的静默时间

数据库与存储运维

5.1 数据库运维要点

  • 索引优化：查询字段必须建索引，避免全表扫描
  • 慢查询排查：控制台查看慢查询日志，优化耗时超过100ms的查询
  • 数据备份：开启自动备份，保留至少7天备份
  • 连接数：云函数中复用数据库连接，避免每次新建

5.2 存储运维要点

  • 设置合理的生命周期，定期清理过期文件
  • 大文件使用分片上传，避免超时
  • 开启 CDN 加速，降低下载费用
  • 配置防盗链，防止资源被恶意盗用

安全配置与权限控制

  • 数据库安全规则：严格配置读写权限，禁止全集合公开读写
  • 存储安全规则：上传文件校验类型和大小
  • 云函数鉴权：敏感接口校验用户登录态，校验权限
  • IP 白名单：管理后台接口限制访问IP
  • 防刷机制：接口添加限流，防止恶意调用

成本优化与资源管控

7.1 云函数成本优化

  • 合理设置内存和超时时间，避免资源浪费
  • 冷启动不敏感的业务，使用预置并发降低冷启动但控制成本
  • 合并小函数，减少函数调用次数
  • 定时清理无用的版本和别名

7.2 数据库与存储成本

  • 定期归档历史数据到冷存储
  • 存储开启智能分层，低频访问自动降成本
  • 避免重复读取相同数据，合理使用缓存

第四章：容器化技术 Docker

Docker 核心概念

  • 镜像（Image）：应用的只读模板，包含代码、运行环境、依赖
  • 容器（Container）：镜像运行的实例，可理解为轻量级虚拟机
  • 仓库（Registry）：存放镜像的地方，如 Docker Hub、腾讯云镜像仓库

1.1 常用命令

# 镜像操作
docker pull nginx            # 拉取镜像
docker images                # 查看本地镜像
docker rmi image_id          # 删除镜像

# 容器操作
docker run -d -p 80:80 nginx # 运行容器
docker ps                    # 查看运行中的容器
docker ps -a                 # 查看所有容器
docker stop container_id     # 停止容器
docker start container_id    # 启动容器
docker rm container_id       # 删除容器
docker logs -f container_id  # 查看容器日志
docker exec -it container_id /bin/bash  # 进入容器

镜像构建与 Dockerfile

2.1 Node.js 项目 Dockerfile 示例

# 基础镜像
FROM node:18-alpine

# 设置工作目录
WORKDIR /app

# 先复制依赖文件，利用缓存
COPY package*.json ./

# 安装依赖
RUN npm install --production

# 复制源码
COPY . .

# 暴露端口
EXPOSE 3000

# 启动命令
CMD ["node", "app.js"]

2.2 构建与运行

# 构建镜像
docker build -t my-node-app:v1 .

# 运行容器
docker run -d -p 3000:3000 --name my-app my-node-app:v1

# 带环境变量运行
docker run -d -p 3000:3000 \
  -e NODE_ENV=production \
  -e DB_HOST=localhost \
  my-node-app:v1
💡 优化技巧

使用 alpine 版本的基础镜像可以大幅减小镜像体积；多阶段构建可以进一步优化，最终镜像只包含运行时依赖。

容器管理与网络

3.1 数据卷挂载

容器内数据是临时的，重要数据需要挂载到宿主机：

# 挂载目录
docker run -d -v /host/path:/container/path image

# 示例：挂载日志目录
docker run -d -p 3000:3000 \
  -v /data/logs:/app/logs \
  my-node-app:v1

3.2 容器网络

# 创建自定义网络
docker network create my-network

# 容器加入同一网络即可通过容器名互通
docker run -d --name db --network my-network mongo
docker run -d --name app --network my-network my-node-app

Docker Compose 编排

用于管理多个容器的应用，一键启动整个服务栈。

docker-compose.yml 示例

version: '3'
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DB_HOST=mongo
    depends_on:
      - mongo
    volumes:
      - ./logs:/app/logs

  mongo:
    image: mongo:5
    ports:
      - "27017:27017"
    volumes:
      - mongo-data:/data/db

volumes:
  mongo-data:

常用命令

docker-compose up -d      # 后台启动
docker-compose down       # 停止并删除
docker-compose logs -f    # 查看日志
docker-compose restart    # 重启服务
docker-compose pull       # 更新镜像

第五章：CI/CD 持续集成部署

CI/CD 核心理念

  • CI（持续集成）：代码提交后自动构建、测试、检查
  • CD（持续部署）：通过验证后自动部署到生产环境
  • 价值：减少人工操作、降低部署风险、提高交付效率

GitHub Actions 实战

2.1 工作流配置文件

在项目根目录创建 .github/workflows/deploy.yml：

name: 部署到 CloudBase

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: 安装 Node.js
        uses: actions/setup-node@v3
        with:
          node-version: '18'

      - name: 安装依赖
        run: npm install

      - name: 安装 CloudBase CLI
        run: npm install -g @cloudbase/cli

      - name: 部署云函数
        env:
          TCB_ENV_ID: ${{ secrets.TCB_ENV_ID }}
          TCB_SECRET_ID: ${{ secrets.TCB_SECRET_ID }}
          TCB_SECRET_KEY: ${{ secrets.TCB_SECRET_KEY }}
        run: tcb functions:deploy --envId $TCB_ENV_ID

监控体系架构

Prometheus + Grafana 入门

2.1 核心组件

  • Grafana：可视化仪表盘，展示监控数据
  • Alertmanager：告警管理，发送通知

2.2 Node.js 接入 Prometheus

const express = require('express');
const prometheus = require('prom-client');

const app = express();

// 注册指标
const httpRequestDuration = new prometheus.Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP请求耗时',
  labelNames: ['method', 'route', 'status']
});

// 中间件统计请求耗时
app.use((req, res, next) => {
  const end = httpRequestDuration.startTimer();
  res.on('finish', () => {
    end({ method: req.method, route: req.route?.path || req.path, status: res.statusCode });
  });
  next();
});

// 暴露指标接口
app.get('/metrics', (req, res) => {
  res.set('Content-Type', prometheus.register.contentType);
  res.end(prometheus.register.metrics());
});

app.listen(3000);

告警规则与通知渠道

4.1 告警级别定义

  • P0（紧急）：服务不可用、核心功能故障 → 电话+短信+企业微信
  • P1（重要）：错误率升高、性能下降 → 企业微信@所有人
  • P2（一般）：非核心异常、资源预警 → 企业微信群消息
  • P3（提示）：日常统计、低风险告警 → 邮件

第七章：运维安全与合规

网络安全基础

1.1 常见攻击类型

  • SQL 注入：通过恶意SQL语句操作数据库 → 使用参数化查询
  • XSS 攻击：注入恶意脚本 → 输入输出转义
  • CSRF 攻击：跨站请求伪造 → Token 校验
  • DDoS 攻击：大量请求打垮服务 → 接入高防CDN
  • 暴力破解：密码穷举 → 限流+验证码+强密码

防火墙与访问控制

# firewalld 操作（CentOS）
systemctl start firewalld       # 启动防火墙
firewall-cmd --list-ports       # 查看开放端口
firewall-cmd --add-port=80/tcp --permanent  # 开放80端口
firewall-cmd --remove-port=80/tcp --permanent
firewall-cmd --reload           # 重载规则

# ufw 操作（Ubuntu）
ufw enable                      # 启用防火墙
ufw allow 80/tcp                # 开放80端口
ufw deny 22                     # 禁止22端口
ufw status                      # 查看状态
⚠️ 重要提醒

远程配置防火墙时千万不要把自己的 SSH 端口封掉，否则会导致无法连接服务器。建议先测试再永久保存规则。

数据备份与恢复

3.1 备份策略

  • 全量备份：完整备份所有数据，占用空间大，恢复快
  • 增量备份：只备份变化的数据，节省空间，恢复慢
  • 建议：每周一次全量备份，每天一次增量备份

3.2 MongoDB 备份脚本示例

#!/bin/bash
BACKUP_DIR="/data/backup"
DATE=$(date +%Y%m%d_%H%M%S)
DB_NAME="mydb"

mkdir -p $BACKUP_DIR
mongodump -d $DB_NAME -o $BACKUP_DIR/$DATE

# 压缩
tar -zcf $BACKUP_DIR/$DATE.tar.gz $BACKUP_DIR/$DATE
rm -rf $BACKUP_DIR/$DATE

# 删除30天前的备份
find $BACKUP_DIR -name "*.tar.gz" -mtime +30 -delete

常见漏洞与防护

  • 及时更新系统和软件包，修补安全漏洞
  • 禁止 root 远程登录，使用普通用户+sudo
  • SSH 修改默认端口，使用密钥登录，禁用密码登录
  • 定期扫描代码依赖漏洞（npm audit）
  • 配置 fail2ban 防止暴力破解

第八章：大中小厂运维实战

中小厂：全栈运维模式

中小公司通常没有专职运维，由开发人员兼任，特点是：

  • 技术选型：优先使用云服务（CloudBase、ECS、RDS），减少自建运维
  • 自动化程度：基础自动化，脚本+定时任务为主
  • 监控告警：云厂商自带监控 + 简单的自定义告警
  • 核心能力：能部署、能排错、能备份、能恢复
💡 给你的建议

如果你在中小团队或独立开发，优先吃透 CloudBase 全栈能力，再掌握基础的 Linux 运维和 Docker，足够应对 90% 以上的场景。

中大厂：DevOps 标准化流程

中等规模公司会有专门的 DevOps 团队，建立标准化的研发运维流程：

  • 代码管理：Git 分支规范、Code Review 流程
  • CI/CD 平台：Jenkins、GitLab CI、云效等统一平台
  • 容器化部署：Kubernetes 容器编排
  • 监控体系：完整的监控、日志、链路追踪
  • 发布流程：灰度发布、蓝绿部署、回滚机制

大厂：SRE 体系与高可用

大厂的 SRE（站点可靠性工程）体系更加专业，关注：

  • 高可用架构：多机房部署、异地容灾、故障自动切换
  • 弹性伸缩：根据流量自动扩缩容
  • 混沌工程：主动注入故障，验证系统稳定性
  • SLA/SLO：服务可用性指标量化与考核
  • 故障演练：定期演练，提升应急响应能力
